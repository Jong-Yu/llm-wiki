# 분석 작업·추출 규약 결정

현재 구현 상태는 [PLAN](PLAN.md), 작업 시 지킬 상세 규칙은 도메인에 연결된 RULES를 따릅니다. 결정 번호·이유와 상세 계약을 보존합니다. 아래 결정 안의 날짜·시험 수·운영 상태는 기록 당시 값이며, 최신 구현 상태는 PLAN을 우선합니다. 필요한 D 번호·하위 절만 읽습니다.

### D-035 — 문서 등록의 맥락 힌트와 Bounded Context 간 대응 검토 (2026-10-23)

상태: 등록 힌트·관리되는 Bounded Context·문서 간 대응 검토의 **설계 후보**입니다. 비교 실험은 수행했지만 입력 필드·저장/버전·MCP 계약과 제품 기능은 미확정·미구현입니다.

이 중 공통 규약과 함께 명시 선택한 맥락을 전달하고 분석 입력 버전에 고정하는 계약은 이후 [D-044]에서 설계했습니다. 관리되는 Bounded Context 등록부·자동 맥락 선택·힌트의 독립 편집 API를 구현하거나 이 절의 후보 전체를 확정한 것은 아닙니다.

- 개념 근거: [Martin Fowler의 Bounded Context 설명](https://martinfowler.com/bliki/BoundedContext.html)은 내부적으로 일관된 모델의 범위와 범위 간 관계를 명시합니다. [Microsoft의 도메인 분석 설명](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis)은 같은 실세계 대상도 업무마다 별도 모델을 가질 수 있고, context map으로 모델 간 상호작용과 책임을 나타낼 수 있다고 설명합니다. D-023에서 참고한 상품의 업무별 차이를 문서 등록과 검토 흐름으로 구체화하는 제안입니다. 이후 공식 원문 네 구절의 비교 실험에서는 맞는 힌트의 우위를 확인하지 못했고, 로컬 정의의 인용만으로 시스템 간 대응을 과하게 확정하는 오류를 확인했습니다. 실제 수치·상한 초과·한계는 [PLAN](../../PLAN.md)의 D-035 실제 결과를 따릅니다.

| 축 | 이 프로젝트에서의 역할 | 예시 |
| --- | --- | --- |
| tenant·권한 | 허용된 자료와 행동을 결정하는 접근 경계 | 회사 또는 독립 프로젝트 공간 |
| Bounded Context | 용어·식별자·규칙이 어떤 업무 모델의 의미로 적용되는지 나타내는 범위 | 카탈로그의 상품, 배송의 출고 단위 |
| 관점 프로필 | 허용된 모델을 어떤 업무 질문과 표현으로 살펴보는지 | 배송 모델의 현업·개발자·아키텍처 관점 |

- 등록 힌트 후보: 주된 서비스/업무 영역, 문서의 목적·대상 독자(원문의 맥락 설명), 용어 정의, 식별자 발급 주체, 참조하는 다른 모델이나 문서를 받을 수 있습니다. 서비스·팀·역할 태그만으로 모델 경계를 확정하지 않습니다. 서비스와 Bounded Context를 항상 일대일로 묶지 않으며 한 문서도 주된 맥락과 다른 맥락의 인용·참조를 함께 포함할 수 있습니다. 구체 필수 필드와 맥락 목록의 관리 방식은 미정입니다. 이 힌트를 접속 사용자의 조회 프로필로 대체하거나 해당 관점만 추출하는 필터로 쓰지 않습니다([D-036]).
- 힌트와 근거: 등록자가 준 힌트, AI가 제안한 맥락, 원문의 실제 관계를 구분합니다. 힌트는 용어 해석·검색·추가 확인을 돕는 입력이고 원문에 없는 관계·식별자·속성의 증거를 대신하지 않습니다. 근거 없는 대응은 검토 후보로 남기며 힌트와 원문이 어긋나면 불일치를 표시합니다. 원문 인용 없는 전문가 판단은 D-031의 별도 권한·Action log를 따릅니다. 힌트 속 명령이 서버 권한·추출 규칙을 바꾸지 않습니다.
- 다른 모델과의 비교: 선택한 같은 워크스페이스의 허용 자료 안에서 양쪽 정의·식별자 발급 범위·속성·조건과 실제 참조 근거를 대조합니다. 동일한 이름만으로 다른 모델을 사용한다고 결론 내리지 않습니다. 검토할 경우에는 같은 모델의 공통 개념인지, 다른 모델의 정의/식별자를 참조하거나 변환하는지, 일부 의미만 대응하는지, 이름만 같은 별개 대상인지와 미확인을 구분하는 방향입니다. 이는 context map의 원리를 참고한 제품 제안이며 모든 DDD 관계 패턴을 새 온톨로지 술어로 구현한다는 뜻은 아닙니다.
- 검토 후보와 판단: 비교 제안에는 양쪽 문서·개념·맥락, 출처·버전, 대응이라고 본 이유와 확인할 질문을 제시하는 방향입니다. 명시 링크, 원문 근거 관계, AI의 대응 추정, 전문가가 확인한 판단을 구분하고 자동 병합하지 않습니다. 다른 맥락의 전문가 정책을 조용히 복사·적용하지 않습니다. 승인 기록은 판단의 출처이며 모델의 동일성이나 진리의 자동 증명이 아닙니다. 검토 권한·후보의 저장/수정/되돌림 계약은 구현 전에 정해야 합니다.
- 호환과 남은 결정: 현재 D-024의 context.domain/viewpoints 및 identifiers.namespace는 업무 영역·관점·식별 범위를 보존하지만, 등록 힌트·관리되는 Bounded Context 식별자·문서 간 대응 검토 원장을 모두 제공하지는 않습니다. 문서 본문이 같아도 힌트나 맥락 정의 변경으로 해석이 달라질 수 있으므로 메타정보의 버전·출처와 파생 결과의 재검토 기준을 별도로 설계해야 합니다. 기존 source_revision만으로 이 변경을 추적했다고 간주하거나 임의 필드를 현재 MCP 인자에 추가하지 않습니다.

원문 비교에서 동명 용어·명시 참조·잘못된 힌트·문서의 복수 모델 범위를 실험했습니다. 다른 tenant 비노출, 힌트/맥락 정의 변경의 버전·재검토와 대응 승인/되돌림은 아직 검증하지 않았습니다. 후속 계약에서는 대응 끝점의 문서·개체 ID·revision과 설명형 표기를 분리하고, AI의 `source_supported` 표시나 양쪽 인용만으로 대응을 확정하지 않아야 합니다. 기존 데이터 보존·버저닝·권한·최신 전문가 판단 조회 계약을 유지하며 이 기록은 여전히 설계 후보입니다. 실제 검증 범위는 [PLAN](../../PLAN.md)을 따릅니다.

### D-044 — MCP 공통 추출 규약·맥락과 분석 입력 버전 관리 (2026-10-24)

상태: **사용자가 요청한 설계 반영**입니다. 각 사용자의 로그인된 CLI가 파일 읽기·AI 본문 구성·온톨로지 추출을 수행하고, 같은 위키 백엔드의 MCP가 단계별 공통 지침·출력 스키마·필요 맥락을 버전과 함께 제공합니다. Electron의 업로드·목록·결과 조회는 [D-043]의 일반 API를 사용합니다. D-043의 작업·저장 래퍼를 확장하는 후속 계약이며 이번에 역할 프롬프트·서버 코드·현행 MCP 인자·운영 권한·원문/그래프/원장을 변경하지 않습니다. 새 도구·규약 배포·실제 AI 연결은 미구현이고 5단계는 미착수입니다.

- 이유: 저장 형식만 통일하면 개체 경계·관계 의미·조건 보존·참고한 정의와 판단이 실행자마다 달라질 수 있습니다. 공통 기준과 입력 출처를 서버에서 고정해야 결과 차이를 추적하고 검토할 수 있습니다. 같은 입력의 동일 JSON이나 의미 정확도를 보장하는 결정은 아닙니다.
- 적용 단위: 같은 tenant에서 승인한 동일 규약 릴리스를 사용합니다. 사용자 계정·조회 프로필을 이유로 의미 규칙이나 전체 원문 추출 범위를 바꾸지 않습니다. 업무 맥락 차이는 명시한 입력 데이터와 적용 범위로 남기며 다른 tenant의 정의·정책을 먼저 읽어 숨기는 방식은 사용하지 않습니다.

#### R2 작업 접수와 CLI 원본 인계 (2026-10-25)

이번 구현은 R2의 작업 수명주기와 CLI의 정확한 원본 수신입니다. Q1/Q2가 아직 없으므로 모든 작업에 `execution_ready=false`, `common_ruleset_required`·`fixed_input_bundle_required`를 반환합니다. 규약 사용·고정 입력·AI 실행·결과 저장이 완료됐다고 표시하지 않습니다. 접수와 실제 분석 결과를 구분하기 위해 이 경계를 선택했습니다.

- `modules/analysis_jobs`가 저장/판단, 일반 API와 tenant MCP가 전송, `client/analysis.py`·`tools.analysis_cli`가 작업 PC의 연결/수신을 맡습니다. API/MCP는 같은 JobStore를 재사용합니다. 사용자/tenant·actor·시각은 서버가 기록하며 생성/claim/update/heartbeat/cancel에는 source_write, 본인 조회에는 read가 필요합니다. 본인 owner marker를 확인한 뒤 state를 읽습니다.
- 생성은 원본 ID/판본/hash·등록 기준과 예정 문서1–8개·원하는 산출물(wiki/ontology)을 고정하고 현재 문서 source/state 기준 또는 부재를 캡처합니다. `_jobs/<id>/state.json`의 전체 events, `leases/<run_id>.json`, `_owners`·`_requests`를 기존 `.registration.lock`에서 다룹니다. intent→owner marker→state→생성 영수증을 보존하며 다중 파일 거래를 약속하지 않습니다. source와 job은 같은 사용자 request_id 공간을 공유해 동작 간 충돌도409입니다. 미확인 요청은 기존 `/requests/{request_id}`에서 영구 intent/owner/state 근거로 확인하며 자동 재생성/초기화하지 않습니다.
- 서버 상태 awaiting_cli/claimed/cancelled, lease none/active/expired, CLI reported_status를 분리합니다. claim은 job CAS에서 run과300초 lease를 발급합니다. 동일 기준의 확인된 claim 재전송은 같은 run을 반환하며 기존 실행을 자동 인계하지 않습니다. 만료 또는 명시 stopped/failed 뒤 재접수는 최신 job 기준과 reclaim=true가 필요합니다. heartbeat는 별도 lease CAS·서버 시각으로 갱신해 job_revision을 바꾸지 않습니다. 원본 기준 변경·만료·취소·다른 run은 진행/원본 인계를 막지만 취소 자체는 현재 권한/job CAS로 가능합니다.
- input_ready/analyzing/blocked/failed/stopped는 CLI의 자기보고입니다. complete/저장 성공 선언은 받지 않습니다. jobs/request 각1000·state/lease events각1000·runs1000·개별 JSON1MiB, 본인 목록 metadata16MiB를 적용합니다. 목록 예산은 tenant 전체 쓰기 quota가 아닙니다. claim은 완성된 state/lease 바이트를 먼저 검사해 한도 실패로 불필요한 lease가 누적되지 않게 합니다.
- 개발 CLI는 같은 기본 URL의 API/MCP에서 인증 사용자·tenant·정책·job/source 기준을 대조한 뒤 정확한 판본의 실제 hash/크기/UTF-8을 확인해 private 로컬 폴더로 받습니다. 임의 URL·redirect·파일명 경로·기존 초안 덮어쓰기·원문 지시 실행은 하지 않습니다. 토큰 파일은 본인만 읽는 일반 파일이며 토큰/로컬 경로를 서버 작업에 보내지 않습니다. 이는 `authenticated_user_tenant_job_match`이고 영구 backend identity·AI 로그인/모델 실행 검증은 아닙니다.

실행은 [README](../../../README.md#분석-작업-접수와-cli-연결), 실제 제한 검증/미실행 범위는 [HISTORY](HISTORY.md#2026-10-25--작업-접수cli-원본-인계)를 따릅니다. 운영 권한·기존 MCP/앱 설정은 유지하고 Q1/Q2·AI 추출/저장·Electron 인계를 다음 요청으로 남깁니다.

#### 공통 규약·고정 입력 연결 (2026-10-25)

기존 의미 정책의 연속 원문14,433 UTF-8바이트를 `.agent/ontology_semantics.md`로 분리하고 로컬 역할과 규약 발행이 같은 원본을 사용합니다. 로컬 협업/평가 운영 절차는 배포하지 않습니다. 기존 평가 도구의 직접 역할 로더도 같은 원문을 조립하도록 연결했습니다. 의미 변경/모델 정확도 승인을 수행한 것은 아닙니다.

규약은 자료 루트 밖의 관리자 발행 영역에 불변으로 공개합니다. 현재 MCP 스키마 조립기를 발행/실행이 공유하고 지원 schema3–6·기본3과 새 제출의 명시적 qualifiers를 대조합니다. manifest 원래 바이트·구성 hash·현재 검증기 호환과 tenant별 기본/허용/철회를 매번 확인합니다. 발행은 관리자 CLI만 제공하며 업무 권한으로 허용하지 않습니다. runtime은 명시한 root/policy만 사용하고 오류에 옛 규약으로 우회하지 않습니다.

입력은 job/run/stage·원본·실제 전체 선택 문서/기계층/검토/정책/이력·관점 정의·규약을 고정해 `_jobs/<job>/inputs/<bundle>/`에 보존합니다. 읽을 때 현재 권한·lease·원본/선택 맥락/관점/규약을 다시 대조합니다. 변경은 새 묶음으로 조정하며 옛 묶음의 바이트를 고치지 않습니다. focus만 추출하지 않고 필수/선택·미확보·scope/완전성을 보존합니다. 구성은 원래 UTF-8 hash에 묶인 문자 페이지로 읽습니다.

read_source 입력의 읽기 결과는 `_extractions/`에 원본/입력/실행 계보·method 자기보고·경고/미독 범위와 함께 불변 제출하고 prepare_wiki에 연결합니다. extract_ontology는 실제 위키 원문·현재 검토 상태에서 준비합니다. 입력 준비 권한은 단계별 source_write/write/ontology_write이며 생성한 묶음 읽기에도 현재 단계 권한을 재검사합니다. 입력8MiB·문자 추출물4MiB·문서8개·묶음/추출물각100의 이번 한도를 적용하며 기존64MiB 추출물 전체 설계를 구현한 것으로 확대하지 않습니다.

CLI의 `--prepare-input`은 정확한 규약/manifest/구성 byte hash를 검증하고 private 인계 폴더에 사본을 보존합니다. 준비 상태는 `can_analyze_input`과 작업의 `input_readiness`로 구분하며 위키/그래프 저장 미구현 조건을 지우지 않습니다. 실행 방법은 [README](../../../README.md#공통-규약과-고정-입력), 실제 제한 검증과 미실행 범위는 [HISTORY](HISTORY.md#2026-10-25--공통-규약고정-입력-연결)에 둡니다.

#### 분석 결과 저장 연결 (2026-10-25)

`modules/analysis_results`가 고정 입력의 위키/기계 그래프 저장·원시 제출·검사 보고·저장 증거를 맡습니다. MCP의 `analysis_job_wiki_write`·`analysis_job_ontology_generate`·`analysis_job_result_query`와 일반 API의 작업별 결과 조회가 이 서비스 하나를 재사용합니다. 기존 직접 저장·그래프 스키마·검토 권한 계약은 유지합니다.

- 위키 `write`, 그래프 `ontology_write`와 본인 job/run·lease·원본·규약·전체 맥락/검토·관점 기준을 확인합니다. 최종 승인은 기존 WikiStore.save/OntologyStore.generate의 선택 `before_commit` 콜백에서 같은 위키 잠금을 보유한 채 수행합니다. 조정 잠금→위키 잠금 순서를 유지하며 public 저장을 중첩 잠금으로 호출하지 않습니다. 그 guard에서 현재 정책/규약 사용을 승인하고, 이미 시작/성공한 저장을 이후 철회로 되돌리지 않습니다.
- 그래프의 원시 JSON을 발행 스키마로 검사해 기본값을 채우기 전 qualifier 생략을 거부합니다. 기존 구조/참조/인용/앵커 검증을 재사용하며 실제 수행 범위만 자동 검사 보고에 기록합니다. 의미 점검은 미실행, 사람 승인은 없음으로 둡니다.
- `_jobs/<job>/results/<request>/`에 정규 JSON 값의 불변 제출을 보관합니다. wire JSON의 공백까지 보존한다고 표시하지 않습니다. 저장 전에 접수/검사 근거를 기록하고, 저장 함수가 반환한 실제 revision의 `saved.json`을 작업 이벤트·최종 영수증과 별도로 보존합니다. 최종 영수증만 실패해도 자료 저장은 반복하지 않습니다. 저장 결과를 알 수 없으면 현재 내용 hash만으로 성공을 발명하지 않으며 `pending_reconcile`/`saved=null`로 둡니다.
- 같은 요청의 같은 제출은 기존 결과를 반환하고 다른 제출은 충돌입니다. 저장 거부도 원시 제출/검사 보고를 보존합니다. 권한 거부 전 다른 소유자의 상태/결과를 읽지 않습니다. 조회에는 현재 read·본인 소유권만 요구해 만료/취소/규약 철회 뒤에도 자기 결과를 확인할 수 있습니다.
- 위키 뒤 그래프 단계는 같은 run의 완료된 위키 영수증과 실제 source/history revision을 연결합니다. 원문의 A→B→A도 계보 대조에 포함합니다. graph/state/source CAS와 기존 generation_id·검토 원장 보존으로 이전 승인을 새 세대에 이식하지 않습니다. 기존 위키만 있는 graph-only 요청은 전체 최신 위키 입력으로 처리합니다.
- source/graph revision은 저장 함수의 실제 결과이며, state_revision은 같은 출력의 저장 직후 관측입니다(`state_revision_basis=post_save_snapshot`). 이후 외부 변경/조회 실패는 현재 출력 상태와 과거 성공 근거를 구분하며 저장을 재시도하지 않습니다. `result_summary`는 실제 요청 근거에서 부분/전체 저장·확인 대기를 집계하고 CLI의 자기보고와 분리합니다.
- 요청 8 MiB·작업별 100개/제출 누적 64 MiB 제한을 적용합니다. 한도 실패로 기존 제출/원장/이력을 정리하지 않습니다. 성공 정리 경고는 저장 성공과 별도로 전달합니다. 불명확한 저장의 자동 복구·개인 AI 실행·Electron·두 PC 실행을 이 묶음의 완료로 확대하지 않습니다.

실행법은 [README](../../../README.md#분석-결과의-위키그래프-저장), 실제 검사는 [HISTORY](HISTORY.md#2026-10-25--분석-결과의-위키그래프-저장-연결)에 기록합니다.

#### 개인 AI 실행 어댑터 (2026-10-25)

첫 실행 제공자는 기존 프로젝트의 검증 도구가 사용하던 개인 Codex CLI로 정했습니다. 모델 API 키를 서버에 추가하는 대신 개인 PC의 CLI 로그인을 사용하고, `tools.analysis_cli --run-ai`를 명시한 경우에만 실행합니다. 원본 인계만 수행하던 기본 명령은 유지합니다. 현재는 UTF-8 원본 4 MiB 이하·단일 대상·POSIX 프로세스 관리로 한정합니다. 다중 대상의 임의 분할과 다른 형식의 변환은 명시 범위가 필요하므로 이번 어댑터가 추정하지 않습니다.

- `client/ai/assembly.py`는 로컬 사본의 전체 hash/소속을 다시 확인하고 발행 규약과 원문/맥락/검토 자료를 구분해 조립합니다. `.md/.txt` 원본은 그대로 UTF-8을 읽어 method=verbatim으로 제출하며 AI의 전사/이해 증명으로 표시하지 않습니다. 위키와 그래프 AI 단계는 각각 새 고정 입력·새 세션을 사용하고 첫 실제 관점/규약을 유지합니다.
- `codex.py`는 명시한 실행 파일을 인자 배열로 시작하고 프롬프트는 stdin으로 보냅니다. 기존 대화를 재개하지 않고 개인 config·프로젝트 지침/호스트 스킬·도구/웹/위임을 실행별 옵션으로 분리합니다. CLI 자체의 시스템 지침/실제 모델 내부 입력 제거까지 독립적으로 증명하지 않습니다. 환경변수는 로그인에 필요한 제한된 목록만 전달하며 위키 토큰/API 키 환경을 넘기지 않습니다. 사용자 설정/로그인을 자동 편집하지 않습니다.
- 구조화 출력용 스키마는 원본과 CLI용 복사본으로 구분하고 원시 결과를 양쪽 모두 검사합니다. 일반 관계에서 mapping 생략과 mapping=null은 기존 검증상 다르므로 CLI 사본만 일반 관계/명시 maps_to의 두 형태로 나눕니다. 원본 발행 스키마·모델 출력값·온톨로지 검증 지문은 바꾸지 않습니다. 위키의 출력 봉투 형식과 서버가 발행한 그래프 스키마도 구분합니다.
- CLI 버전·요청/관측 모델·정확한 prompt/schema/output hash를 로컬에 남기고 결과 저장의 선택 execution 인자로 연결합니다. 서버는 허용한 키/길이/hash 형식만 확인해 receipt.execution.origin=client_reported로 보존합니다. 작성자/시각/승인 위조 키는 거부하며 실제 계정·의미 정확도·사람 승인을 인증하지 않습니다. execution 생략 시 기존 제출 payload/hash는 유지합니다.
- `lease.py`가 30초마다 기존 heartbeat API를 호출합니다. 갱신 실패/취소/시간 초과에는 자기 CLI 프로세스 그룹을 종료·회수하고 다음 저장을 막습니다. 서버의 source/state/job CAS와 현재 권한 검사는 그대로 재사용합니다. 응답을 잃은 저장은 같은 request_id로 조회만 하며 원문 hash만으로 성공을 추정하거나 쓰기를 자동 재전송하지 않습니다.
- 성공 완료는 실제 서버 영수증과 result_summary에서 확인합니다. CLI는 종료를 stopped로 보고하고 complete를 자기보고하지 않습니다. 그래프 실패로 성공한 위키를 반복 저장하지 않고 입력·출력·실패 기록을 보존합니다. 기존 backend execution_ready는 PC의 로그인/실행 능력을 증명하지 않으며 실행 CLI의 handoff_readiness와 ai_execution 결과를 나눕니다.

구체 명령은 [README](../../../README.md#개인-ai-실행-어댑터), 실제 핵심 검사와 작은 실제 CLI 확인은 [HISTORY](HISTORY.md#2026-10-25--개인-ai-실행-어댑터)에 둡니다. Electron/PTY 자동 입력·실제 두 PC·Windows 네이티브·다른 제공자·원문 의미 정확도는 이번 완료 범위로 확대하지 않습니다.

#### 공통 지침의 원본과 배포

초기 의미 지침은 현재 [.agent/wiki_ontology.toml](../../../.agent/wiki_ontology.toml)의 개체 유형·술어/방향·인용·조건/예외·식별 범위·속성·후보·출처·제출 전 점검을 재사용합니다. 스키마는 `core/modules/ontology/validation.py`·`values.py`·`constants.py`의 실제 검증 계약과 `core/mcp/schemas.py`의 입력 모델에 대조합니다. [D-024]·[D-036]의 원문 충실성·전체 추출 원칙을 유지하며 새 의미 규칙이나 작은 실험용 출력 상한을 이번에 추가하지 않습니다.

파일 읽기 단계에는 형식별 지원 도구/입력·원본 판본/hash 확인·페이지/시트/셀 대응·누락 보고를, 본문 구성 단계에는 원문 의미/조건·표·인용 위치의 보존과 AI 전사/재구성의 출처 구분을 포함하도록 후속 규약을 준비합니다. 온톨로지 의미 지침은 기존 기준을 유지합니다. 이 추가 단계 지침은 이번에 역할 프롬프트나 실행 규약으로 구현하지 않으며, 현재 온톨로지 역할 파일만으로 PDF/OCR/Excel 읽기까지 지원한다고 표시하지 않습니다.

후속 구현에서는 의미 지침을 `.agent/`의 공통 원본으로 한 번 분리하고, 역할 프롬프트와 서버 릴리스가 이 원본을 참조/조립하도록 합니다. 프로젝트 경로·AGENTS/PLAN 읽기·역할 호출·파일 담당·분리 평가 운영 절차는 로컬 역할에 남깁니다. 전체 역할 파일을 원격 AI의 작업 지침으로 배포하거나 같은 의미 지침을 역할/도구 설명/문서에 각각 수동 복제하지 않습니다. 도구 설명은 규약을 받는 진입점과 필수 보존 원칙을 안내합니다.

서버 관리자가 명시적으로 발행한 규약만 사용합니다. 규약에는 지침 본문, 실제 출력 스키마, 용어·관계 정의, 개발용 예시, 호환 조건과 변경 이유를 묶고 각 구성 바이트의 SHA-256을 manifest에 기록합니다. 릴리스 manifest의 정확한 UTF-8 바이트 hash를 `ruleset_revision`으로 사용하며 manifest 자체 안에 자기 hash를 넣지 않습니다. 규약 ID/버전 표시는 내용을 대신하지 않고, 같은 ID·버전의 내용을 덮어쓰지 않습니다. 스키마와 서버 검증기가 어긋난 릴리스는 발행/사용을 거부합니다. 개발용 예시와 비공개 평가 정답·검증 질문·옛 점수는 구분하며 후자를 배포물에 넣지 않습니다.

규약 릴리스와 tenant별 기본/사용 허용 규약 설정은 tenant 자료 루트 밖의 검증된 서버 설정·배포 영역에서 관리합니다. 다른 tenant의 업무 정의·비밀·토큰을 공통 릴리스에 넣지 않습니다. 읽기·원본 등록·그래프 쓰기·전문가 정책 권한은 규약 발행 권한이 아니며, 발행은 서버 관리 변경으로 분리합니다. 현재 권한 parser나 read13을 확장하지 않습니다. 불변 릴리스와 작업 입력의 보존 사본은 실행 이력이며 수동 편집하는 두 번째 지침 원본이 아닙니다.

#### 규약·맥락·작업 입력의 별도 버전

| 대상 | 보존할 식별·버전과 의미 |
| --- | --- |
| 출력 스키마 | 현행 `schema_version=3`과 정확한 스키마 hash. 지침 개정만으로 그래프 스키마 숫자를 올리지 않음 |
| 공통 규약 | `ruleset_id/ruleset_version/ruleset_revision`, 구성별 hash·호환 서버/스키마·발행 기록. 표시 버전과 내용 hash를 구분 |
| 작업별 입력 묶음 | 서버 발급 `bundle_id/bundle_revision`, `job_id/run_id/stage`, 실제 전달 내용과 참조 manifest. 원본/맥락/규약의 어느 하나가 달라도 새 묶음 |
| 원문과 변환 계보 | D-043의 원본 판본/hash·호스트 수신 바이트 hash·CLI의 읽기/변환 제출 extraction ID/hash·선택/미독 범위와, 그래프 단계의 실제 `document/source_revision`. 서버 수신 검증과 CLI 실행 자기보고를 구분하며 서로 대체하지 않음 |
| 정의·조건·예외 등 맥락 | 문서/원문 revision·인용 줄, 기계 그래프의 `graph_revision`, 검토의 `claim_id/state_revision`, 정책의 `event_id`·정확한 적용 범위와 상태 |
| 조회와 실행 정보 | 허용 profile 정의·접근정책 revision, 요청/포함/미포함 범위, 필수 여부·완전성, 서버 관측과 CLI 자기보고를 구분한 모델/설정·입력 조립 기록 |

`bundle_revision`은 전달할 불변 manifest 바이트의 SHA-256이며 구성별 내용 hash를 포함합니다. ID는 서버가 발급하고 hash를 권한·사람 승인·실제 모델 실행 증명으로 사용하지 않습니다. 입력 manifest/구성 바이트·원시 제출·실제 저장 영수증은 D-043의 tenant 내 `_jobs/<job_id>/`에 보존합니다. 현재 그래프가 바뀌어도 당시 규약·입력·제출을 재구성할 수 있어야 합니다. 위키 본문이나 v3 `provenance`에 규약 버전·외부 정책·실행 출처를 억지로 넣지 않으며 기존 `_history`·`_reviews`를 대체하지 않습니다.

#### 필요한 맥락의 선택과 출처 보존

- 대상 원문은 해당 단계의 명시 범위 전체를 제공합니다. 필요한 정의·조건·예외 문서는 요청자/검토자가 같은 tenant의 허용 문서에서 명시 선택하고, 각 문서가 필요한 이유와 필수 구성(원문·검토 상태 등)을 입력 목록에 고정합니다. 서버는 선택된 집합을 공통으로 제공하며 아직 선택하지 않은 관련 문서를 자동으로 모두 찾았다고 표시하지 않습니다. 목록 변경은 새 입력 묶음으로 준비합니다. 자동 선택·전역 의미 검색·관리되는 Bounded Context 등록부는 별도 후속 범위입니다.
- 원문/기계층은 [D-027]의 보존 캡처를 재사용하고, 현재 검토·전문가 판단은 [D-028]·[D-031]의 조회 로직으로 별도 캡처합니다. `effective_graph/policies`와 미검토·보류·`pending_history`, `active/other_scope/pending/inactive`, 실제 한정어·범위·출처를 함께 남깁니다. `ontology_context`의 machine층만으로 전문가 판단을 확보했다고 하지 않습니다. 명시적으로 이력 없음/해당 정책 없음이 확인된 상태와 조회 실패를 구분합니다.
- 선택 문서의 전체 원문과 다른 관점·미분류 제약을 유지합니다. profile의 `focus`만 뽑거나 기존 유효 그래프 일부를 새 전체 추출 결과로 재전송하지 않습니다. 기존 그래프가 없는 신규 문서는 그 사실을 기록하고, 필수 원문/검토 상태가 확보됐다면 선택적 machine 그래프 부재만으로 차단하지 않습니다.
- 외부 정의·기존 판단·등록 힌트는 해석 참고이며 대상 원문 사실의 evidence가 아닙니다. 원문과 어긋나면 차이·확인 질문을 남깁니다. 이전 거절/정책에 맞추어 원문 명시 주장을 지우거나 기존 승인을 새 세대에 이식하지 않습니다. 외부 문서에만 있는 사실은 원래 문서의 출처에 유지하며 대상 문서 인용으로 위장하지 않습니다. 힌트로 `context.domain`·식별자를 발명하지 않습니다.
- D-035의 등록 힌트를 함께 제공하려면 작성 주체·정확한 본문·대상 범위·내용 hash를 입력 manifest에 별도로 고정합니다. ‘힌트 없음’도 명시합니다. 이는 해당 작업의 입력 보존 계약이며 독립 힌트 편집 API·관리되는 맥락 정의 저장소를 구현했다는 뜻이 아닙니다. 기계적으로 바뀌는 현재 힌트를 옛 묶음에 끼워 넣지 않습니다.
- 모든 구성에 요청/포함 범위와 `complete/truncated/skipped`·필수/선택·읽기 실패·원문/그래프 현재성을 보존합니다. 기존 문서당 1 MiB와 D-027의 문서 수·캡처/응답 예산을 유지하고 규약·검토·힌트도 실제 입력 예산에 합산합니다. 그 한도 안에서 단일 응답이 크면 고정된 hash/페이지의 구성별 조회로 전달하며 페이지 분할로 전체 한도를 우회하거나 몰래 요약·절단하지 않습니다. 필수 자료가 없거나 읽지 못했거나 선택한 범위를 해당 CLI의 입력 한도 안에 보존할 수 없으면 ‘맥락/범위 확인 필요’로 멈춥니다. 선택적 구성의 누락도 표시하며 불완전한 입력을 전체 맥락 확보로 보고하지 않습니다.
- 원문·힌트·참조문서 속 명령은 데이터입니다. 서버 관리자가 발행한 규약 본문만 추출 지침으로 조립하고, 원문·참고 맥락은 종류와 출처가 있는 데이터 블록으로 전달합니다. 입력 자료가 tenant·권한·규약·저장 기준을 바꾸지 못합니다.

#### MCP 제공과 개인 CLI의 단계별 실행

아래 이름과 필드는 **후속 도구/작업 래퍼 설계**입니다. 현재 MCP 목록/인자나 실행 명령에 추가된 기능이 아닙니다.

| 표면 | 책임과 반환 |
| --- | --- |
| 새 `extraction_rules_read` | 허용 tenant의 기본 또는 명시한 사용 가능 규약 릴리스를 읽음. 정확한 지침·스키마·예시·구성별 hash와 호환/사용 상태 반환; 조회 중 최신 내용으로 바꿔 끼우지 않음 |
| 새 `analysis_job_input_prepare` | 본인 claim/run·stage·`expected_job_revision`에서 규약과 명시 입력/맥락을 캡처하고 불변 묶음을 발급. `read_source`는 원본/파일 참조, `prepare_wiki`는 성공한 불변 extraction, `extract_ontology`는 실제 저장 본문/revision을 입력으로 고정. **작업 metadata 변경**이며 read-only 도구가 아님. 고정 bundle과 새 job_revision을 반환 |
| 새 `analysis_job_input_read` | job에 연결된 정확한 bundle/구성을 고정 페이지로 읽음. 각 페이지가 같은 bundle revision과 구성 hash에 속함을 확인. 페이지 수신/클라이언트 확인은 실제 AI의 이해·준수 증명이 아님 |
| D-043의 단계 저장 래퍼 | `analysis_job_wiki_write`·`analysis_job_ontology_generate`에 해당 `bundle_id/bundle_revision`을 연결. 서버가 보관한 job/run/stage·규약·의존 버전·payload hash와 실제 저장 영수증을 대조 |

규약/묶음 읽기는 현재 tenant의 read와 작업 조회 범위를 검사합니다. 준비와 제출/저장은 매번 현재 인증 주체·본인 claim/run·lease·취소·등록/job 기준과 단계 권한을 확인합니다. `read_source` 입력 준비와 추출물 서버 제출에는 D-043의 새 `source_write`, `prepare_wiki` 입력 준비/본문 저장에는 `write`, `extract_ontology` 입력 준비/그래프 저장에는 `ontology_write`가 필요합니다. 로컬 읽기 능력이 이 권한을 대신하지 않습니다. 입력 묶음 발급은 저장 승인이나 권한 양도가 아니며 토큰·원격 PC 절대 경로를 지침/manifest에 넣지 않습니다. source_write로 본문/그래프를 저장하지 못하며 기존 직접 저장의 권한은 변경하지 않습니다.

1. **요청/접수:** D-043 작업 생성에서 사용할 규약 릴리스를 고정하고 맥락 문서 목록·필수 구성·힌트를 기록합니다. CLI는 access_context와 claim 후 정확한 서버 규약을 조회합니다. 로컬 파일·옛 대화의 규약을 기본값으로 대신하지 않습니다. 같은 릴리스가 없는 클라이언트도 서버에서 받아야 하며 미지원 스키마/입력 방식이면 분석 전에 차단합니다.
2. **파일 읽기 입력:** 원본 판본/hash·파일 참조·선택 범위와 단계 지침을 `stage=read_source`의 불변 묶음으로 발급합니다. 아직 생성하지 않은 extraction을 필수 입력으로 요구하지 않습니다. 호스트 bridge가 같은 서버의 파일 API에서 받은 실제 바이트를 확인하고 CLI에 작업용 파일을 제공합니다.
3. **CLI 파일 읽기·제출:** CLI가 지원하는 로컬 도구/OCR/이미지 입력과 AI로 원본을 읽고, 해당 read_source bundle에 연결해 D-043의 `source_extraction_submit`으로 문자/표/산출물 참조·manifest를 제출합니다. 서버는 이를 불변 extraction으로 보관하고 영수증/새 job_revision을 반환합니다. 읽지 못한 영역과 도구 출력/AI 전사·재구성을 구분하며 제출 성공을 원문 충실성 승인으로 해석하지 않습니다.
4. **위키 본문 준비·저장:** 성공한 extraction의 정확한 ID/hash·원본·선택 범위·맥락을 고정해 `stage=prepare_wiki`의 **새** 묶음을 발급합니다. CLI의 AI가 이 입력에서 충실한 본문과 원본 대응을 구성해 해당 묶음의 위키 저장 래퍼로 저장합니다. 앞 묶음에 새 추출물을 끼워 넣지 않으며 원본/추출물 hash를 위키 revision으로 사용하지 않습니다.
5. **온톨로지 준비:** 성공한 위키 영수증과 실제 wiki_read 본문/revision, 기존 그래프/검토 상태를 캡처해 `stage=extract_ontology`의 새 묶음을 발급합니다. 앞 단계 bundle/영수증을 선행 참조로 연결합니다. 신규 문서는 검토 이력 없음 상태를 보존합니다. 그래프 추출은 이 실제 전체 본문을 대상으로 합니다.
6. **개인 AI 실행:** CLI 어댑터는 각 AI 단계에 공통 규약·스키마·고정 원문/읽기 자료·구분된 맥락만 넣은 새 추출 세션을 준비하고 정확한 조립 입력 hash와 확인 가능한 실행 정보를 남깁니다. 사용자 요청은 문서/범위/원하는 산출물을 지정하며 공통 의미 기준을 조용히 덮어쓰지 않습니다. 기존 대화의 불필요한 지시·다른 tenant 내용은 전달하지 않습니다. 세션 분리·구조화 입력·필요한 파일/이미지 입력을 지원하지 않는 임의 터미널은 요청 준비/어댑터 확인 필요로 두며 그 경로를 공통 실행 검증 완료로 표시하지 않습니다.
7. **제출/확인:** 클라이언트가 원시 결과와 bundle 참조를 제출하면 서버는 현재 허용 규약·입력 연결·의존 버전·권한·source/state CAS 및 기존 구조/인용/한도를 검사합니다. 성공 영수증에 규약·단계 입력·원시 제출 hash·실제 document/source/graph/state revision을 연결합니다. 형식/인용 저장 성공은 ‘저장 완료·미검토’이며 사람 승인으로 올리지 않습니다. 그래프 실패 때문에 성공한 본문을 다시 쓰지 않습니다. Electron은 D-043의 일반 API로 이 영수증과 현재 결과를 조회합니다.

서버가 고정한 입력과 실제 모델에 들어간 입력은 구분합니다. CLI가 보고한 모델/설정/조립 hash는 자기보고로 표기하고, 서버 발급·전달 기록과 섞지 않습니다. 서버는 개인 AI의 숨은 시스템 지침·설정·과거 대화 제거·실제 지침 준수를 독립적으로 증명할 수 없습니다. 동일 규약은 결과 비교의 기준이며 계정/모델 간 동일 출력 보장이 아닙니다.

#### 기준 변경·경쟁·이력과 기존 기능의 경계

- 새 규약을 기본값으로 발행해도 진행 중 job의 고정 릴리스나 기존 그래프를 바꾸지 않습니다. 기존 허용 릴리스로 시작한 작업은 그 입력으로 마칠 수 있고, 새 작업은 새 기본값을 받습니다. 명시적으로 사용 철회한 릴리스는 이후 준비/저장을 차단하고 초안을 보존합니다. 관리자에 의한 옛 릴리스 재허용도 새 설정 변경으로 기록하며 자동 fallback하지 않습니다. 규약/묶음/제출 이력은 보존하고 이전 릴리스의 hash만 최신값으로 바꾸지 않습니다.
- 대상 원문·등록 판본·선택한 정의/예외·검토/정책·힌트 또는 사용한 profile 정의/정확한 적용 범위가 바뀌면 다음 저장에서 ‘입력 기준 변경’을 반환합니다. 해당 묶음의 모든 고정 의존 버전을 비교하고 초안을 보존한 뒤 새 입력으로 재대조/필요한 단계 재추출을 합니다. 필수 맥락을 빼거나 버전값만 바꾸어 기존 결과를 재전송하지 않습니다. 자기 위키 저장의 성공 영수증으로 다음 단계 묶음을 만드는 것은 외부 변경 수용과 구분합니다.
- 준비 캡처와 최종 저장의 일관성은 D-043의 **등록/작업 조정 잠금 → 기존 저장 잠금** 순서를 유지합니다. 최종 의존 대조와 저장은 기존 저장 모듈의 잠금 아래 같은 임계구역에서 수행하도록 공용 내부 실행 경계를 재사용/확장하며, 래퍼의 사전 검사와 실제 저장 사이에 다른 문서/검토 쓰기가 끼어들 수 있는 상태로 구현하지 않습니다. 잠금을 잡고 public save/generate를 다시 호출하는 중첩 잠금은 금지합니다. 규약 사용 철회도 단계 실행 승인과 직렬화하고, 이미 시작/성공한 저장은 결과를 보존하며 후속 단계만 막습니다. 이 경계의 실제 경합 검증 전에는 원자성을 검증했다고 하지 않습니다.
- 규약 구버전·참고 맥락 변경·입력 불완전·규약 출처 미기록은 원문/그래프 `stale`과 별도로 결과/작업 조회에 표시합니다. 이 설계에서 기존 stale 의미·`needs_reextraction` 판정을 바꾸지 않습니다. 과거 입력 출처가 없는 운영 그래프에 새 규약 버전을 소급 부착하거나 당시 준수로 인증하지 않습니다.
- 기존 wiki_write/ontology_generate 및 검토/정책 API 계약은 유지합니다. 기존 도구의 직접 저장에는 작업 규약 사용을 인증하지 않으며 ‘공통 입력 확인 없음’으로 구분합니다. 공동 추출의 규약 사용 표시는 새 작업 래퍼에서 영수증이 확인된 결과에만 부여합니다. 직접 저장 전체를 차단하는 권한/마이그레이션 정책은 별도 운영 결정이며 현재 권한을 자동 변경하지 않습니다.
- D-043의 intent/멱등 영수증·부분 실패·`pending_reconcile`·`storage_busy`·성공 정리 경고 처리를 재사용합니다. 입력 기록 공개 실패는 자료 저장 전에 멈추고, 실제 자료 저장 뒤 영수증만 실패하면 저장을 반복하지 않습니다. 규약/맥락 변경만으로 자동 재추출·옛 승인 이식·정책 전파를 하지 않습니다.

운영 공통 입력과 원문 분리 평가는 구분합니다. D-021의 생성자는 고정 원문·중립 스키마·고정 추출 지침만 받고 기존 그래프/정책·검증 질문·옛 점수·다른 세션 이력을 자동 첨부하지 않습니다. 공통 규약의 의미 조항을 평가용으로 고정할 수 있으나 평가 입력 제한을 운영 묶음으로 우회하지 않습니다. 비교 기준은 D-036의 의미 충실성·반복 일관성·전문가 조정·판단 지속성이며, ID/배열 순서와 의미 차이를 구분합니다.

구현 순서와 수용 검사는 [PLAN의 D-044 후속 범위](../../history/2026-10-25-before-domain-split/PLAN.md#d-044-공통-추출-규약맥락버전-후속-구현과-검증-계획)에서 관리합니다. 이번에는 설계 문서의 연결·일관성만 검증하며 실제 규약 배포·전송·추출 품질이나 여러 사람의 사용을 검증하지 않습니다.

#### Rule 분류·검증·위반 처리 (2026-10-25)

상태: **사용자가 요청한 상세 설계 반영 / 규약 배포·검증 보고·작업 래퍼 구현 및 실행 미착수**입니다. D-044의 공통 규약을 아래 자동 검사 규칙과 의미 검토 규칙으로 분류하고 위반 처리까지 정합니다. 기존 의미 지침의 판단 기준을 재사용하며 이번에는 코드·역할 프롬프트·그래프 스키마·운영 권한을 변경하지 않습니다. 아래 Rule ID·보고 항목·처리는 후속 규약/작업 계약이며 현재 MCP 인자에 추가된 기능이 아닙니다.

**보장 단위와 이유.** 자동 검사는 서버가 확인할 수 있는 형식·문자열·참조·고정 입력 조건에 한정합니다. 의미 검토는 원문이 주장을 지지하는지, 조건과 핵심 내용이 보존됐는지 판단합니다. 같은 Rule의 자동 부분과 의미 부분을 각각 판정하고 한쪽 통과로 다른 쪽을 통과시키지 않습니다. 보장할 수 있는 표시는 ‘이 입력·제출에 대해 지정한 자동 검사 통과’이며, 전체 Rule 준수·의미 정확도·누락률·모델 간 동일 결과 또는 실제 사람 승인을 인증하는 표시는 아닙니다. 이 표시는 새 작업 래퍼의 검사/저장 영수증이 있는 결과에만 붙입니다. 기존 직접 저장과 과거 그래프에는 ‘공통 입력 확인 없음’을 유지합니다.

**규약에 포함할 Rule 명세.** 각 Rule은 `rule_id`, 검사 분류(automatic/semantic), 적용 단계/스키마, 정확한 요구사항, 자동 검증기 ID/내용 hash 또는 의미 검토 질문, 위반 시 처리, 개발용 정상/실패 예시를 포함합니다. 발행 시 ID 고유성·참조 검증기/스키마 존재·검증 범위 일치를 검사합니다. 의미를 바꾼 개정은 새 불변 릴리스와 변경 이유로 발행하고 옛 명세를 보존합니다. AI에게 줄 지침과 서버 검사기가 같은 명세를 사용하며 비공개 평가 질문/정답은 포함하지 않습니다. 자동 검증기가 준비되지 않은 규칙을 automatic 통과로 발행하지 않습니다. 해당 기능이 필요한 규약 릴리스의 사용을 막거나, 검사 범위를 명시한 새 릴리스를 발행합니다.

##### 검사 보고와 위반 시 처리

보고는 D-043의 tenant 내 `_jobs/<job_id>/`에 입력/원시 제출/저장 영수증과 연결해 보존합니다. 그래프 컬렉션이나 v3/v4 provenance, 위키 본문, `_reviews/`에 새 보고 필드를 억지로 넣지 않습니다. 읽기/기록은 같은 job·tenant의 권한을 따르며 권한 오류에 다른 tenant의 원문/존재/검사 세부를 반환하지 않습니다. 초안/보고 보존도 접근·수신/저장 한도를 따릅니다. 수신 거부·보고 기록 실패로 서버 보존을 확인하지 못하면 클라이언트 초안을 유지하고 보존 미확인을 표시하며, 무제한 원시 제출 보관을 약속하지 않습니다. 다음 항목은 **후속 작업 기록의 논리 계약**이며 기존 MCP에 임의 인자로 보내지 않습니다.

- 보고 식별·기준: 서버 발급 보고 ID, job/run/stage·bundle revision·ruleset revision, 적용 스키마/검증기 revision, 원시 제출 hash와 실제 저장 영수증/그래프·state revision의 연결을 유지합니다. 내용이 바뀐 제출은 새 hash/보고이며 옛 보고를 덮어쓰지 않습니다.
- 자동 항목 결과: Rule ID별 `pass/fail/not_run/not_applicable/error`와 검사 범위·이유를 남깁니다. 적용 안 됨에는 이유가 필요하고, 첫 오류 때문에 뒤 검사를 실행하지 못했으면 not_run입니다. fail·필수 검사의 not_run/error가 있으면 저장을 차단합니다. 진단 응답 한도로 보고가 잘렸으면 그 사실을 표시하고 검사 통과/전체 문제 보고로 해석하지 않습니다.
- 의미 항목 결과: Rule ID·판정·검토자 종류(AI 자기점검/별도 AI/실제 사람)·검토한 원문 범위·실제 연속 인용/줄·대상 주장·발견 이유·권고·미해결 이유를 기록합니다. 원문 없는 모델 점수/요약만으로 지지·위반을 확정하지 않습니다. AI 검토자·모델/설정/입력 조립 기록은 자기보고 여부를 표시하고 서버 인증 주체·기록 시각과 구분합니다.
- 대상 참조: 저장 전에는 문서/source revision·제출 hash·컬렉션/배열 위치를 함께 사용합니다. 저장 뒤에는 실제 graph revision을 연결하고, claim이 있는 관계/속성/후보에만 claim_id/state revision을 연결합니다. 개체나 누락 지적에 가짜 claim ID를 만들지 않으며, 새 세대에서 옛 위치/claim ID를 현재 대상으로 사용하지 않습니다. Rule 보고는 검토 제안이며 현재 claim 상태를 직접 바꾸지 않습니다.
- 누락/표현 한계: 대응 주장이 없어도 source revision·실제 원문 위치·관련 질문·생략 사유·영향 범위를 기록합니다. omissions와 보고는 job의 별도 자료이며 그래프 생성 인자에 추가하지 않습니다. ‘한도 때문에 버림’을 의미 보존 통과나 schema_limit의 자동 정당화로 삼지 않습니다.

**실행 순서.** 규약/입력을 고정한 뒤 CLI가 추출·자기점검하고, 서버는 원시 제출 검사와 기존 검증기를 실행합니다. 유효한 제출의 저장은 D-043/D-044의 조정 잠금→저장 잠금 안에서 현재 권한·의존 revision·철회 상태를 다시 대조한 뒤 수행합니다. 사전 검사 보고만으로 이후 저장을 허용하지 않습니다. 성공하면 검사 범위와 실제 저장 영수증을 연결하고 ‘저장 완료·미검토’를 표시합니다. 의미 제안은 위 표대로 연결하며 원문 기반 정정·원문 정정·업무 판단을 각각의 기존 경로로 처리합니다. 별도 LLM 의미 검사 호출/제공자·예산·어댑터는 미구현이며 이번 설계가 서버의 자동 모델 호출을 추가하지 않습니다.

**최소 예시.** 원문이 ‘승인된 경우에만 시스템 A가 장치 B를 사용한다.’이고 실제 전체 인용과 유효한 끝점으로 uses를 제출했다면, 다섯 qualifiers 키를 명시하고 condition=null로 낸 결과는 자동 검사상 유효할 수 있습니다. 의미 검토 R-S05에서는 조건 손실을 찾아 condition에 실제 구절 ‘승인된 경우에만’을 보존하도록 제안합니다. condition 키 자체를 생략했다면 새 공통 래퍼의 R-A08 위반이며, 원문에 없는 인용을 붙였다면 R-A07 위반입니다. ‘경우/만’ 키워드가 보인다는 사실만으로 조건 손실을 확정하지 않습니다.

### D-052 — MCP 진단 보존·버전별 제출·작업 공통 기준 (2026-10-25)

사용자가 MCP 정책 점검의 우선순위1 세 항목을 구현하도록 요청했습니다. D-044의 공통 작업 경로를 다음과 같이 확장합니다. 기존 직접 wiki_write/ontology_generate·저장 그래프·검토 원장과 업무 권한은 유지합니다.

- **진단과 저장의 분리:** `analysis_job_wiki_write`와 `analysis_job_ontology_generate`는 선택 `diagnostics` 및 `save`(기본 true)를 받습니다. 진단은 발행된 `diagnostics.schema.json`의 경고·누락·미독·검토 범위·R-S01~10 의견/인용/초안 대상을 사용합니다. 그래프 컬렉션에 추가하지 않고 기존 `_jobs/.../results` 불변 원시 제출과 영수증에 연결합니다. 원문 인용·줄·배열 대상과 최대256KiB/목록100개를 검사하며 source/bundle/ruleset·원시 제출 hash를 보존합니다. 위키 준비의 인용은 불변 추출 문자, 그래프 단계의 인용은 실제 고정 위키 본문에서 확인합니다. 의미 판정과 human_reported는 클라이언트 보고이며 사람 승인으로 인증하지 않습니다.
- **초안/실패와 조회:** `save=false`는 같은 단계 권한·본인 작업·현재 입력/CAS를 확인하고 `state=draft`, `saved=false`로 원시 초안/진단만 보존합니다. 초안의 그래프 형식 검사는 통과로 표시하지 않습니다. save=true에서 신고된 미독, 위키 준비의 누락은 자료 저장을 막고 보고를 남깁니다. 그래프의 의미상 의심/표현 한계만으로 자동 거절·승인/후보 전환하지 않습니다. 기존 `analysis_job_result_query`와 HTTP 결과 GET이 거부/초안/저장 보고를 반환하고 취소·권한 회수 뒤에도 본인의 read 조회를 유지합니다. 영수증 유실은 saved.json의 실제 성공 근거와 진단을 복원하며 재저장하지 않습니다. 기존 한도/멱등/정리 경고 계약을 따릅니다.
- **버전별 지침/형식:** 기본3과 지원3–6을 유지하며 각 버전의 허용 술어·끝점·mapping·출처 관계 한정어를 발행 JSON Schema에도 반영합니다. 공통 의미 원문에 v4 앵커·v5 대응·v6 출처 사용 경계를 추가하고 버전별 개발 예시를 실제 저장 검증기와 대조합니다. 개인 CLI는 `{content,diagnostics}` 또는 `{submission,diagnostics}` 응답을 받아 그래프와 진단을 별도 인자로 전달합니다. 이 구조 검증은 실제 모델 의미 정확도 검증이 아닙니다.
- **작업 공통 기준:** 최초 input_prepare에서 규약·명시 맥락/판본·관점·모든 출력 대상의 기준을 job 이벤트의 불변 basis로 고정합니다. 맥락 생략은 승계이며 명시 빈 목록·다른 허용 규약·맥락/대상/검토 변경은 조용히 채택하지 않습니다. 자기 단계 저장에 의한 변화만 동일 job/run/basis의 실제 영수증·source/graph/state/전체 이력 연쇄로 확인해 승계합니다. 출력 대상이 필수 맥락과 겹쳐도 검사에서 제외하지 않습니다. 단순 재claim은 기준을 바꾸지 않습니다.
- **명시 재준비와 호환:** `analysis_job_input_prepare(stage=read_source,rebase=true,rebase_reason=...,expected_job_revision=...)`만 새 작업 기준을 발급합니다. 새 기준에서는 옛 bundle/extraction을 저장 입력으로 재사용하지 않으며 실제 자료·옛 보고/영수증은 보존합니다. 이전 run/basis의 저장·조정 대기를 현재 완료 집계에 합치지 않고 개별 이력으로 남깁니다. 공통 기준이 없는 옛 진행 작업은 analysis_basis_required와 legacy_rebase_required로 명시 재준비를 요구합니다. 기존 릴리스는 덮어쓰지 않습니다. 진단 구성/버전별 제출이 없는 릴리스는 ruleset_incompatible이며 운영 적용에는 새 버전 발행·명시 허용 설정·업데이트된 서버 실행이 필요합니다.

규칙별 자동 판정 세분화, 별도 의미 검사 실행, 원본 위치 대응·새 형식 변환과 비교/복구 계약은 이 변경의 완료 범위에 포함하지 않습니다. 실제 검증·한계는 [HISTORY](HISTORY.md), 현재 범위는 [PLAN](PLAN.md)을 따릅니다.

### D-056 — 규칙별 검사 보고·개인 별도 의미 검사와 기존 규약 호환 (2026-10-25)

규칙별 실행 결과를 묶음 상태와 분리하고 별도 의미 검사를 개인 실행기에 연결합니다. 구조 통과·의미 의견·실제 저장·사람 승인을 서로 대신하지 않기 위한 선택입니다. 기존 그래프 의미 스키마와 추출 의미 원문은 변경하지 않습니다.

- `validation_report.rule_results`는 R-A01~10 각각의 `rule_id/status/checker/reason`을 담습니다. 상태는 `pass/fail/not_run/not_applicable/error`입니다. 실제 실행한 규약·권한·고정 입력·스키마·인용·참조·한정어·메타데이터·후보 검사를 기존 검증기로 확인합니다. 앞 검사가 거부되면 뒤 검사는 `not_run`, 해당 그래프 항목이 없으면 `not_applicable`, 저장 잠금/검사 운영 오류는 `error`로 남깁니다. 기존 `automatic/checks` 필드는 호환하며 검사 입력/원문 판본·규약·제출 hash는 `basis`에 보존합니다. `save=false`는 현재 기준과 진단 인용만 검증하므로 그래프 검사 통과를 선언하지 않습니다.
- 진단 v2는 기존 경고·누락·미독·검토 범위·findings에 R-S01~10의 `rule_results`와 `semantic_check`를 더합니다. 모든 규칙은 한 번씩 나타나며 사유를 요구합니다. 실패는 같은 규칙의 실제 인용 finding에 연결하고, 미실행/판단 불가·검사 오류·적용 대상 없음도 이유를 보존합니다. 표현 한계는 `schema_limit` finding으로 남기며 다른 술어로 강제 변환하지 않습니다. 부분 의견만 있는 v1을 규칙별 pass로 소급 해석하지 않습니다.
- 별도 AI 보고는 check ID, job/run/bundle/revision, 대상 원문 revision, 원시 제출 hash, 그래프 schema version, ruleset ID/version/revision을 정확히 대조합니다. 원문 우선 검토 기록과 그 hash, 두 실행의 CLI/prompt/schema/output hash도 보존합니다. 서버의 구조/인용 검사와 별개로 `origin=client_reported`, `human_approval=false`이며 `human_reported`도 사람의 업무 승인 인증이 아닙니다. 기존 검토 원장에는 이벤트를 만들지 않습니다.
- `core/client/semantic_check.py`는 기존 개인 Codex 어댑터를 두 새 세션으로 호출합니다. 첫 세션은 고정 원문 전체·중립 스키마만 보고 중요한 사실·조건·누락 질문을 고정합니다. 다음 세션은 그 기록·원문·중립 제출을 대조하며 생성 프롬프트·생성자 진단·후보 reason/question을 받지 않습니다. 원시 제출 hash와 검증용 제출 hash는 별도 보존합니다. 생성/검증 분리는 입력 제한이며 OS 격리·외부 독립 심사·의미 정확도 인증이 아닙니다. 실제 원문 평가를 수행할 때는 ontology EVALUATION의 새 원문·새 세션 조건을 별도로 적용합니다.
- `--semantic-check`는 개인 CLI의 명시 선택입니다. 기존 작업의 사용권·현재 기준 아래 실행하고, 생성자 진단을 보존한 채 별도 결과를 새 request ID의 기존 `analysis_job_ontology_generate(diagnostics=..., save=false)`에 기록합니다. 실제 그래프 저장은 별도 요청이며 별도 검사의 fail/error가 자동 승인·주장 삭제·변환을 유발하지 않습니다. 모델/보고 오류는 error 보고, 취소는 로컬 not_run 보고를 보존합니다. 서버가 모델/셸을 실행하지 않고 MCP 도구를 기계적으로 늘리지 않습니다.
- 새 발행의 diagnostics schema는 v1/v2를 지원합니다. 서버는 기존 v1 발행 바이트도 계속 허용하고, 각 입력이 고정한 발행 스키마를 준수합니다. v1 전용 규약에서 별도 v2 검사를 명시 실행하면 모델 호출 전에 새 규약 필요 오류를 반환합니다. 불변 릴리스 덮어쓰기·운영 기본/허용 정책 변경·실서버 업데이트는 이번 구현이 자동 수행하지 않습니다.

실제 검증과 미실행 범위는 [HISTORY](HISTORY.md#2026-10-25--규칙별-판정별도-의미-검사)를 따릅니다.

### D-058 — 규약 허용 정책의 명시 전환·전체 보존·되돌림 (2026-10-25)

불변 발행과 tenant별 허용/기본값 전환을 분리하고 로컬 관리자 도구 `tools.transition_ruleset`에 inspect→plan→apply 및 status→rollback→apply를 둡니다. 원격 MCP 사용자 권한을 관리자 권한으로 확장하지 않습니다. 운영 대상이 미확정이면 격리 발행·검증과 실행 절차만 완료하고 운영 적용으로 기록하지 않습니다.

- 계획은 root/policy·현재 정책 전체 바이트 hash·전후 전체 정책·현재 검증기·허용 릴리스 revision에 연결합니다. 적용 시 같은 정책 잠금과 CAS로 확인하고 전체 전후 내용을 새 불변 이력에 동기화한 뒤 원자 교체합니다. 이력 실패는 변경을 막으며 기존 릴리스/이력을 덮어쓰지 않습니다. 같은 잠금을 따르지 않는 외부 편집기와의 완전한 직렬화는 약속하지 않습니다.
- 기존 허용은 보존하고 기본값 변경은 명시 옵션입니다. 철회된 릴리스를 묵시적으로 재허용하지 않습니다. 신규 정책/tenant의 첫 허용은 해당 릴리스를 기본값으로 정합니다. 현재 reader와 관리자 도구가 동일한 정책 parser를 사용합니다.
- 되돌림은 대상 event의 적용 후 전체 hash가 현재와 일치할 때만 원래 전체 바이트를 새 이력과 함께 복원합니다. 중간 변경을 덮어쓰지 않으며 최초 생성 되돌림은 삭제 대신 빈 유효 정책을 남깁니다. `ruleset_busy`는 동일 계획 재시도, `ruleset_conflict`는 최신 내용 대조 후 새 계획, 적용 후 디렉터리 동기화 경고는 이미 완료된 변경과 구분합니다.
- 구 v1 릴리스와 이미 고정한 작업은 유지합니다. 기본값 전환이 기존 job을 rebase하지 않으며 새 규약 선택에는 기존 명시 rebase 계약을 적용합니다. 구버전 영수증은 현재 read/소유권으로 조회하고 재실행에는 현재 규약 허용을 요구합니다. 상세 실행과 실제환경 경계는 [전환 절차](RULESET_ROLLOUT.md)를 따릅니다.

### D-061 — 별도 의미 검사 상태 계약과 부분 보고 보존 (2026-10-26)

공개 RFC9111 개발 사례의 별도 모델은 R-S02·R-S05·R-S10의 `schema_limit` 발견을 `not_run`에 연결했습니다. 기존 검증기의 거부는 올바르지만, 지시문의 미확정 안내와 표현 한계 안내가 상태 조합을 분명히 하지 않았고 전체 실패 보고가 다른 유효한 규칙의 근거까지 가렸습니다. 서버 검증을 완화하거나 모델의 의미 판정을 바꾸지 않고 출력 제약과 실패 보존을 보완합니다.

- `pass`는 원문 대조를 마친 지지 판단이며 `supported`와 양립합니다. `fail`은 인용으로 확인한 모순·근거 없음·조건 손실·누락·표현 손실이며 같은 규칙의 문제 finding을 요구합니다. `schema_limit`은 실제 남은 표현 손실을 확인했다는 판정이므로 `fail`에 연결합니다. 기존 속성·한정어·원문 문자열로 보존할 수 있는 의미와 전용 기계식 논리 필드의 부재를 구분합니다. 이 fail은 의미 검토 의견이며 canonical 저장 거부나 사람의 승인이 아닙니다.
- `not_run`은 미검사/판단 미확정으로 `ambiguous/not_run/undetermined`만 연결합니다. `not_applicable`은 적용 대상이 없는 상태이며 findings가 없습니다. `error`는 검사 실행·보고 오류입니다. 표현 손실을 이미 확인한 상태를 불확실하다는 이유로 `not_run`이나 `pass`로 바꾸지 않습니다.
- 별도 검사 모델만 사용하는 `assessment_schema()`는 R-S01~10을 고정 키로 요구하고 각 상태 분기에서 허용 verdict를 제한합니다. 모델은 규칙 안에 findings를 넣으며, 클라이언트는 내용·인용·대상을 그대로 두고 저장용 rule ID와 배열 참조만 부여합니다. 공개 진단 v1/v2 스키마와 기존 릴리스 바이트는 바꾸지 않습니다. v1 전용 입력의 별도 v2 검사 사전 거부도 유지합니다.
- 원시 `assessment/result.json`·`assessment.json`과 내용 변경 없는 배열 투영 `assessed-diagnostics.json`을 별도로 보존합니다. 전체 구조·입력 기준·실행 기록이 유효한 보고에서 규칙/인용/대상 오류가 발생하면, 해당 규칙만 `error`인 파생 보고를 만들고 최종 전체 검증을 다시 통과시킵니다. 유효한 다른 규칙과 인용 finding의 verdict는 그대로 유지하며 인덱스만 정확히 다시 연결합니다. 잘못된 finding은 원시 보고에 남고 검증된 파생 보고에 포함하지 않습니다. `failure.json`은 오류 규칙·원래 상태·원래 finding 위치·오류 코드와 실제 존재하는 원시 파일 참조를 남깁니다.
- 전역 형식·입력/감사 hash·실행 기록·전체 범위/한도 오류는 부분 통과로 만들지 않습니다. 전체 `error` 보고와 원시 산출물을 보존하며 모델을 자동 재호출하지 않습니다. 저장 서버는 원래 잘못된 보고를 계속 거부하고 불변 요청에 보존합니다. 파생 보고는 기존 새 request ID의 `save=false` 결과로 보관하며 원문·그래프·검토 원장·사람 승인 상태를 바꾸지 않습니다.

RFC9111은 개발 회귀 자료이며 원시 판정/기존 평가를 고치지 않습니다. 새 원문 실제 모델 평가는 별도 담당의 확정 근거를 기다리며 이번 구조·인용·저장 검사를 의미 정확도 개선 완료로 확대하지 않습니다. 실제 실행 범위는 [HISTORY](HISTORY.md#2026-10-26--별도-의미-검사-상태-충돌과-부분-보고-보존)에 기록합니다.

### D-065 — Codex·Claude 실행 기록과 고정 규약 호환 (2026-10-26)

기존 질문·분석·추출안·별도 의미 검사 흐름을 유지하면서 개인 실행 제공자를 `codex` 또는 `claude`로 선택합니다. CLI는 `--ai-provider`와 제공자별 실행 파일을 받고 기존 입력 고정·사용권·권한·CAS·영수증 복구를 재사용합니다. Electron은 현재 실행과 다음 시작 선택을 구분하며, 기존 v1 설정은 Codex로 읽고 명시 저장할 때 v2로 보관합니다. 모델 제공자를 바꿔도 이전 실행 기록을 새 제공자의 기록으로 바꾸거나 실패 시 다른 제공자로 자동 대체하지 않습니다.

서버 실행 정보와 별도 검사 실행 정보는 두 제공자를 허용합니다. 기존 진단 규약의 실행 제공자 제한만으로 Claude의 실제 실행 기록이 거절되지 않도록, 서버가 아는 정확한 이전 스키마에 한해서 `CheckExecution.provider`만 확장한 검증 사본을 사용합니다. 기존 발행 파일·고정 입력·hash·revision·정책은 그대로 보존하고, 다른 스키마에는 이 예외를 적용하지 않습니다. 신규 발행 스키마는 두 제공자를 명시합니다. v1에 v2 기능을 추가하거나 인용·상태·의미 규칙을 완화하지 않습니다.

이유: 제공자 식별 메타데이터의 확장을 위해 기존 작업과 불변 규약을 교체할 필요가 없습니다. 실제 실행 제공자를 정확히 기록하면서 기존 모델 결과·저장·복구 동작을 유지합니다. 구조화 출력과 계약 검증은 모델 의미 정확도 또는 사람 승인을 뜻하지 않습니다. 구현 검증과 실제 모델 미검증 범위는 각 도메인 HISTORY에 기록합니다.
