# 관계·판단 색인과 질문 전 근거 조회 연결안

상태: **2026-11-08 최초 조사 때 작성한 설계 초안을 보존한 문서.** 이후 사용자 요청으로 [D-124](DECISIONS.md#d-124--기존-관계판단-색인과-첫-답변-전-고정-근거-제공-2026-11-08)의 질문 투영·허용 공간 검색·v6 초기 근거 영수증을 구현했습니다. 최신 구현/로컬 검증·미검증 범위는 [PLAN](PLAN.md)·[HISTORY](HISTORY.md#2026-11-08--질문용-색인과-첫-ai-호출-전-근거-제공-d-124)를 따릅니다. 이하의 제안/미구현 표시는 최초 조사 시점 기준입니다. 실제 AI/비교 실험·운영 자료 변경은 하지 않았습니다.

## 목표와 결론

질문마다 모델이 검색 계획을 먼저 만들게 하는 대신, 앱이 저장된 관계·판단에서 관련 후보를 찾고 원문 구절·현재 판단을 첫 답변 호출에 제공한다. 자료가 늘어나도 모델에는 질문에 필요한 제한된 묶음만 전달한다. 색인 구축·조회 자체에는 모델을 쓰지 않는다.

재추출이나 새로운 정본 저장소는 필요 없다. **기존 재생성 가능 SQLite에 질문용 투영을 추가하고, 기존 고정 근거·조회 영수증·인용 검증에 연결하는 것이 제안 범위다.** 검색은 관련 후보를 찾으며, 자연어 질문의 의미와 근거의 충분성은 답변 모델이 판단한다. 충분하면 첫 호출에서 답하고, 부족하면 기존 추가 조회를 사용한다. 모든 질문의 1회 호출이나 절감률은 아직 입증하지 않았다.

## 그대로 붙일 수 없는 부분

1. **지도에 보이는 관계만으로 판단을 검색할 수 없다.** 현재 `_project`는 `effective_graph`를 기준으로 관계를 만들고 `reject/defer`를 제외한다. `condition`도 본문 대신 존재 여부만 투영한다. 질문용으로는 빠진 판단과 실제 조건이 필요하다.
2. **현재 표시와 보존된 판단이 다르다.** `capture_documents.document()`의 `entry.claims`는 정리된 `current_claims`를 쓰며, 원래 `claims/history`는 `entry.snapshot`·원장에 남는다. 반려 기록이 Clean Up으로 숨겨졌다고 판단 근거가 사라진 것으로 해석하면 안 된다. 독립 관계는 원래 `claims`에 합쳐지지 않으므로 `authored_relations/relation_history`도 읽어야 한다.
3. **주장 조회만으로 이유와 인용이 완성되지 않는다.** `_claim_items()`는 판단과 원문 값을 내보내지만 검토 이유는 별도 이력 항목이다. `c` 인용은 원래 추출 값의 인용문에 연결된다. 수정된 값·전문가 정책의 근거를 그 원래 인용 하나로 대신할 수 없다.
4. **선택한 문서 밖의 예외는 현재 질문에 들어오지 않는다.** `prepare_question`은 선택 문서를 캡처하고 `_basis`가 사용자 턴 저장 시 고정한다. 질문 실행 단계에서 다른 문서를 몰래 추가하는 방식은 범위·입력 고정을 위반한다.
5. **현재성 확인도 선택 문서 기준이다.** `workflow_io.observe_basis()`는 고정한 문서·원본과 접근 범위를 대조한다. 전체 공간 검색 후 고르지 않은 문서에 새 예외가 생긴 경우까지 감지하려면 검색 범위의 판본도 별도로 결합해야 한다.

## 제안 1: 기존 SQLite에 질문용 투영 추가

지도 API와 투영은 유지하고, 같은 `read_index_rows`에 별도 namespace `question_grounding_v1`을 제안한다. 현재의 범용 JSON payload와 owner 교체를 사용하므로 이 설계만으로 공통 DB 스키마 변경을 요구하지 않는다. 현재 검색은 `instr(title, ?)` 부분 일치이며 전문 검색·벡터 검색이 이미 있는 것으로 가정하지 않는다.

| 투영 행 | 필드·원본 | 용도 |
| --- | --- | --- |
| 개체/검색어 | document ID·경로, entity ID, label/type, context, identifiers의 namespace/value, 원본 판본 | 이름·식별자에서 문서 내 개체 후보를 찾는다. 현재 스키마에 독립 alias 필드는 없다. AI로 별칭을 만들지 않는다. |
| 주장/판단 | 원래 collection/claim ID, 원문 값과 현재 검토 값의 참조, 양쪽 끝점, predicate/property, **전체 qualifiers/context/provenance**, decision/needs_review, review·policy·relation event 참조 | 관계·속성·후보와 그 판단을 함께 검색한다. 원문 값과 수정 값 양쪽 용어를 검색 대상으로 둔다. |
| 적용 상태 | current/archived, active/pending/inactive/other_scope, origin, ambiguity | 현재 사실·보류·반려·정리된 이력·다른 관점의 판단을 구분한다. |
| 근거 참조 | source/graph/review/history/state revision, 원문 인용 위치·hash, ledger 종류와 event ID | 본문·전체 이력을 색인에 복제하지 않고 정본 또는 고정 근거에서 정확한 항목을 읽는다. |
| 문서 manifest | 파일 서명, 문서 상태, 색인 버전, skipped/truncated, 추출 상태, 판단 계산 가능 여부 | 색인이 최신인지와 조회 범위의 부족을 따로 보고한다. |

개체 키는 문서·세대에 결합한다. 같은 이름, 식별자 값 또는 `same_as/view_of`만으로 문서 간 개체를 병합하지 않는다. 다른 문서의 같은 이름은 관련 후보로 함께 찾되 동일성은 미확정으로 표시한다. 주장 키에는 문서·collection·claim ID와 모호성/중복 구분을 포함하고, 이력 키는 ledger 종류와 event ID를 함께 사용한다. 배열 위치를 영구 식별자로 저장하지 않는다.

투영 입력은 기존 검토 계산 결과를 사용한다. 정상 주장과 현재 독립 관계뿐 아니라 반려·보류·정리된 판단, 적용 정책과 그 출처도 검색 가능하게 둔다. 과거·다른 범위의 이벤트는 경고/감사 근거로 보존하며 현재 사실로 올리지 않는다. 전문가 정책에 원문 인용을 발명하지 않는다.

쓰기 경로는 유지한다. 기존 변경 관측과 배경 준비에 질문 투영을 연결하고, 원문 편집·재추출·검토·정책·독립 관계·되돌림·Clean Up의 변경 문서를 갱신한다. 가능하면 잠금 안에서 한 번 캡처한 결과로 지도/질문 투영을 각각 만든다. 색인 실패가 이미 성공한 정본 저장의 실패나 저장 재시도를 유발하지 않는다. 손상 색인을 임의 삭제하지 않는다. 권한·tenant·사용자·profile·domain/viewpoint·access 기준으로 분리하고 매 요청 현재 인가를 먼저 확인한다.

## 제안 2: 질문에서 후보와 관련 판단을 함께 찾기

추가 분류 모델 없이 다음 순서로 로컬 조회한다.

1. 질문의 Unicode 정규화·대소문자 정리 후, 명시한 문서/개체 참조·식별자·저장된 이름·구체 용어를 사용한다. 식별자 정확 일치 → 이름/문맥 일치 → 관계·속성·조건·검토 이유의 문자 일치를 후보 신호로 삼는다. 이름/용어용 검색 행과 기존 SQL 필터를 재사용한다.
2. 일치 개체의 관계를 양방향으로 찾고 **원문 값·수정 값·반려·보류·적용 정책·독립 관계와 그 이유**를 함께 확장한다. 긍정 관계만 점수가 높아 반대 근거를 밀어내지 않도록 한다.
3. 관련 끝점과 식별 맥락을 중심으로 검토 묶음을 만들고, 같은 쌍의 서로 다른 predicate·극성·조건도 함께 확인한다. 이 묶음은 검토 후보 집합이지 자동 모순 판정이나 논리 추론 결과가 아니다. 서로 다른 문서의 동명이인은 병합 없이 나란히 제공한다.
4. 원문 단락 검색을 함께 사용한다. 추출되지 않은 예외까지 관계 색인이 보장하지는 않는다. 미분석·stale 문서, 모호한 이름, 추출 누락 가능성과 검색의 문자 일치 범위를 표시하고 필요한 경우 기존 원문 조회로 이어간다.

`A → B 반려`는 `A → B를 현재 근거로 채택하지 않음`이다. **`A → B가 성립하지 않음`은 원문/정책에 명시된 부정과 그 적용 조건이 있어야 한다.** 미검색·미검토·미분류·보류·정리된 과거 기록도 각각 유지한다. 일반 지식과 다른지 먼저 모델에게 물어보지 않고, 일반적인 질문에도 같은 프로젝트 조회를 수행한다.

대명사·새로운 표현·한국어/영문 간 의미 대응을 문자 검색만으로 모두 해석할 수는 없다. 후속 질문은 명시된 대상 참조와 사용자 대화 문맥을 함께 제공하고, 대상이 불명확하면 기존 모델의 추가 조회/사용자 확인으로 넘긴다. 이번 초안은 번역·별칭·의미 검색용 모델을 추가하지 않는다.

## 제안 3: 검색 범위를 근거 고정 전에 정하기

두 범위를 새 계약에서 명시적으로 구분한다. 현재 `explicit_selection_only`의 의미는 유지한다.

| 범위 | 동작 |
| --- | --- |
| 선택 문서 | 지금 허용·선택한 문서 안에서 먼저 찾는다. 선택 밖의 예외를 확인했다고 말하지 않는다. 기존 경로에 먼저 연결할 수 있다. |
| 허용 워크스페이스 | 질문과 선택한 시작점을 사용해 현재 허용 공간의 색인을 조회한다. 관련 문서·예외 판단을 **사용자 질문의 근거 고정 전**에 추가하고 검색 범위·선택 이유·검색 판본을 보관한다. 전체 공간 예외를 확인하려는 목표에는 이 경로까지 필요하다. |

구체 연결 지점은 `personal.router.append_turn()` → `_basis()`다. 현재 `_basis`는 context request만 받는다. 신규 범위에서는 사용자 질문과 조회 범위를 함께 전달해 문서 후보를 정한 뒤 기존 `prepare_question()`과 `QuestionBasisStore.freeze()`를 호출하는 안을 제안한다. 이미 저장한 질문·근거를 수정하거나 실행 중 문서를 추가하지 않는다.

문서 후보의 판본과 실제 캡처 판본을 대조한다. 선택 문서와 관련 판단은 일치하되 전체 공간의 원자적 스냅샷을 새로 보장한다고 주장하지 않는다. 전체 공간 모드에서는 검색 시작·캡처 종료의 발견 판본이 다르면 준비 충돌로 처리한다. 현재 한도인 문서8개·원본4개, 조립8 MiB·고정 묶음16 MiB를 올리지 않는다. 필수 예외 묶음이 한도를 넘으면 전체 확인으로 완료하지 않고 범위 부족을 알린다. 기존 v5 도구는 고정 범위 밖을 검색하지 못하므로, 그 경우 후속 질문의 범위 재준비나 향후 명시적 확장 계약이 필요하다.

전체 공간 검색의 발견 판본에는 문서 목록과 그래프·검토 등 질문 투영의 기준을 결합한다. `observe_basis/_fresh`에서 선택하지 않은 문서의 추가·수정·판단 변경도 보수적으로 변경으로 감지하도록 확장한다. 관리된 쓰기는 기존 변경 원장으로 확인하고, 관측 단절/직접 파일 변경은 재대조 또는 불확실 상태로 처리한다. 색인 파일의 mtime이나 배경 작업 완료만으로 현재성을 증명하지 않는다. 기존 개인 기록→Wiki 잠금 순서를 유지하며 이미 잠근 경로에서 `prepare_index()`의 잠금을 재획득하지 않는다.

## 제안 4: 첫 답변 호출에 실제 근거를 전달하기

```text
사용자 질문 + 명시한 검색 범위
  → 로컬 색인에서 관련 문서·관계·판단 후보 찾기
  → 기존 prepare_question / freeze로 판본 고정
  → 고정 묶음 안에서 후보 재검증·초기 선택 계획 보관
  → 실행 claim 후 근거 영수증 1회 생성·수신 (모델 호출 없음)
  → 원문 구절 + 현재 판단/이유 + 적용 조건을 첫 모델 입력으로 전달
  → 충분하면 답변 / 부족하면 기존 도구로 추가 조회
```

신규 질문 계약 `personal-question-v6`를 제안한다. v5의 고정 입력·영수증·실행 중 작업은 변경하지 않는다. 별도 전역/CLI 설정은 필요 없다.

- **선택 계획:** 질문·검색 범위·발견 판본·basis snapshot·정확한 claim/event 참조·선정/누락 사유·조회 정책 버전을 고정한다. `QuestionRunStore.create/_input`에서 신규 입력 지문에 결합한다. 모델 출력이나 이전 답변으로 검색 계획을 만들지 않는다.
- **묶음 조립:** `question_evidence.py`에 선택 참조 기반의 내부 조립을 추가하는 안이다. `_claim_items/_history_items`, 원문 범위 처리와 `resolve_evidence_ids`의 검증을 공유한다. 실시간 색인은 위치 후보일 뿐이며 실제 항목은 **해당 질문의 불변 basis**에서 다시 찾는다.
- **내용:** 질문에 관련된 원문 구절, 판단 전후 값, 현재 적용 상태·조건, 연결된 이유/정책/독립 관계 이벤트를 제공한다. 관련 없는 전체 이력과 중복 구절은 보내지 않는다. 수정 값의 실제 원문과 검토 이벤트를 함께 제공하고, 정책은 실제 Action log로 인용한다.
- **제공 기록:** 신규 v6의 `/evidence` 초기 묶음 동작으로 기존 `operation=evidence` 영수증을 남긴다. 현재 권한·소유·basis 현재성·활성 run/lease·CAS·요청 재접수 검사를 유지한다. 응답 손실은 같은 요청 영수증으로 복구한다. 재획득한 실행은 자기 실행의 새 제공 기록을 요구한다.
- **클라이언트:** 첫 `guarded_model()` 전에 초기 영수증을 받아 `_append_evidence()`로 reads/registry에 등록한다. `_grounded_citations()`와 제출 시 `_validate_citations()`는 이번 실행이 실제 제공한 ID만 허용한다. 모델에게 전달되지 않은 색인 ID를 인용 가능 ID로 취급하지 않는다. v6 인계·API 입력/응답·클라이언트 계약 소비부를 함께 확장해야 한다.

초기 묶음은 **기존6회 조회 중1회**, 응답은 기존24 KiB 안에서 계산하는 안이다. 추가 조회는 남은5회다. 내부 조립의 문서 수·후보 수·원문 범위·바이트 상한도 별도로 제한하고 기록하여, RPC1회라는 이유로 무제한 내부 검색을 숨기지 않는다. 중요한 반대 판단이나 조건은 한 묶음으로 취급하고, 공간 부족 시 일부만 보내 완전한 답처럼 만들지 않는다. `truncated/skipped/next`와 빠진 묶음의 참조를 제공해 추가 조회나 범위 재준비로 넘긴다.

색인 최신성, 문서 추출 상태, 후보 조회의 범위, 초기 제공 범위, 의미상 충분성은 별개다. 예를 들어 색인이 정상이어도 추출된 관계에 문서의 모든 예외가 담겼다는 뜻은 아니다. `근거 없음`을 프로젝트에서 일반 관계가 성립한다는 증거로 쓰지 않는다. 일반 설명을 제공할 때도 프로젝트 적용 여부와 구분한다.

## 최소 구현 순서와 향후 완료 기준

1. **질문 투영:** 새 질문용 namespace와 조회를 추가하고 기존 관측/배경 준비에 연결한다. 지도 응답·정본 파일·추출·검토 규칙은 유지한다.
2. **선택 범위의 v6 연결:** 고정 근거 안의 초기 선택 계획→조회 영수증→첫 모델 입력→인용 제출을 연결한다. 이 단계만으로 전체 공간 예외 발견을 완료했다고 표시하지 않는다.
3. **전체 공간 준비 연결:** 질문 접수 전에 관련 문서를 찾고, 발견 판본·현재성·한도 초과를 근거 묶음에 결합한다. 이 단계까지 있어야 문서가 늘어날 때 필요한 자료를 자동으로 고르는 흐름이 된다.

향후 구현에서는 명시 부정과 반려의 구분, 수정 인용·정책 event, 독립 관계/undo, Clean Up 전후 판단 보존, 다른 관점·옛 세대, 동명이인, 미분석/추출 누락·stale·색인 실패, 선택 밖 예외와 새 문서 추가, 묶음 한도·누락 표시, 고정 후 변경·권한 철회·재획득·영수증 복구를 확인해야 한다. 후보 선택 경로에 모델 호출이 없고, 초기 근거가 실제 인용 등록을 거친다는 것도 확인 대상이다. 이번 조사에서는 이러한 실행 검증이나 새 품질·토큰 비교를 하지 않았다.

토큰 절감의 구조적 목표는 `계획→검색→재계획→읽기`의 모델 왕복을 줄이는 것이다. 검색/색인 크기와 서버의 저장·조립 비용까지 일정해지는 것은 아니다. 답변 품질·실제 호출 수·토큰 감소는 구현 후 별도 확인 전까지 미확정으로 둔다.
