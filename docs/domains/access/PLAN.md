# 인증·워크스페이스 계획

## 현재 상태

- 이름 가입·로그인, 사용자별 암호화 영구 토큰, 본인 범위의 access_revision을 구현했습니다. 기존 version 1 정책·사용자/공간 ID·개인 자료와 Bearer 인증을 유지합니다. [D-071](DECISIONS.md#d-071--소규모-poc-가입로그인과-사용자별-영구-토큰-2026-10-28).
- 신규 가입은 계정·보호 인증정보만 만들고 소속·업무 권한 없이 배정을 기다립니다. `memberships: {}`, `default_tenant: null`이며 `sdv-platform` 자동 생성·배정은 하지 않습니다. 앱의 배정 대기·토큰 재확인·재시작을 연결한 개발본입니다. [D-132](DECISIONS.md#d-132--신규-가입과-관리자-워크스페이스-배정-분리-2026-11-17).
- PoC 앱은 허용 공간의 중립 기본 조회를 사용하고 이전 역할 선택을 복원하지 않습니다. 서버의 profile/API/MCP 호환과 사용자·tenant·행동 권한 검사는 유지합니다. [D-083](DECISIONS.md#d-083--poc에서-역할별-조회-관점-제외-2026-10-29).
- 기존 일반 토큰 서버의 시작 호환을 확인했습니다. 암호문·미완료 가입·알 수 없는 항목·링크가 있으면 키를 임의 재생성하지 않습니다. 기존 토큰·정책의 자동 이관은 하지 않습니다. [검증 기록](HISTORY.md#2026-10-29--기존-개인-토큰-서버의-시작-호환).
- 사용자 요청에 따른 단일 계정의 기존 공간 배정·권한 확대는 수행했습니다. 관리자 콘솔 구현이나 신규 가입의 자동 배정은 아니며 해당 사용자의 실제 앱 재확인은 남아 있습니다. [운영 기록](HISTORY.md#2026-11-19--요청한-신규-계정의-sdv-플랫폼-배정).

### 관리자 기능: 설계·시안

독립 서버 관리자 콘솔의 공간·사용자 검색, 대상 고정 배정, 권한 확인, 대상 내부 이력과 별도 관리자 인증을 [통합 설계](WORKSPACE_ADMIN_DESIGN.md)에 정리했습니다. 로그인·배정 대기·설정에서의 진입과 취소/종료 복귀는 모의 시안입니다. **제품 관리자 인증/API/화면은 미구현이며 운영 적용 완료가 아닙니다.**

다음 범위는 관리자 인증·기능 범위 확정 후 저장/인증 경계 → API → 앱 연결입니다. 배정의 개별 저장·영수증과 기존 정책·토큰·자료 보존을 [설계 완료 조건](WORKSPACE_ADMIN_DESIGN.md#8-구현-순서와-완료-조건)에 따라 검증합니다.

## 공개 구현 계약

- 서버는 `initialize_auth()`로 검증한 AuthService를 조립합니다. 기존 정책·tenant root 오류에서 빈 정책/자료 루트를 만들지 않습니다. 자격 증명 키와 credentials는 자료 루트 밖에 보관합니다. 키 선택은 명시 경로 → LLM_WIKI_CREDENTIAL_KEY_FILE → 정책 부모 credential.key 순서이며 새 파일 0600·폴더 0700입니다. 암호문이 있는데 키가 없거나 잘못됐으면 교체·재발급 대신 실패합니다.
- 공개 예외는 tenant 정책 모드의 정확한 `POST /api/v1/auth/signup`, `POST /api/v1/auth/login`뿐입니다. 요청은 `{name}`이며 응답 data에는 token/user_id/display_name/memberships/default_tenant/policy_revision/access_revision이 있습니다. access-context는 토큰을 제외한 같은 신원·범위를 제공합니다. Host/Origin·본문 제한과 `Cache-Control: no-store`를 유지합니다.
- access_revision은 본인 ID·소속·유효 권한·허용 profile·인증 세대를 반영합니다. 다른 사용자·표시 이름·JSON 공백 변경으로 무효화하지 않으며 policy_revision은 전체 정책 감사용으로 보존합니다. 과거 actor/hash는 재작성하지 않습니다.
- 기존 사용자에 복구 암호문이 없으면 이름 로그인은 실패하고 Bearer 인증은 유지합니다. `enroll_existing_token()`은 현재 정책 해시와 맞는 알려진 토큰만 명시 등록합니다. 키 교체·재암호화·사용자 ID 변경을 자동 수행하지 않습니다. 가입 한도는 기존 사용자를 포함한 5명입니다.
- `.auth.lock`과 `.signup.pending.json`으로 가입을 직렬화하고 의도 → 암호문 → 정책 순서로 확정합니다. 새 가입은 `new_tenant: false`이고 이전 true 의도는 원래 공간·소속까지 복구합니다. 관리자 쓰기도 같은 잠금을 사용하거나 서버를 중지합니다. 기준 정책 변경은 실패시키며 성공 후 복구 기록 정리 경고로 토큰을 재발급하지 않습니다.
- 중복 이름은 409 name_conflict, 사용자 한도는 409 user_limit, 없는 이름은 401 login_failed, 키/복구/정책 실패는 503 access_unavailable입니다. 로그인 실패를 자동 가입으로 바꾸지 않습니다.

## 남은 검증

관리자 제품 구현과 기존 사용자 토큰의 명시 암호화 등록·원격 재로그인은 별도 확인이 필요합니다. 신규 가입 정책의 배포·운영 범위는 [플랫폼 배포 상태](../platform/PLAN.md#배포와-개발본)와 해당 실행 기록을 함께 확인합니다. 다른 사용자의 자료 보존, 권한 회수, 동시 가입·부분 실패·응답 유실은 격리 검증하며 운영 자격 증명으로 쓰기 시험하지 않습니다. SSO는 현재 PoC 범위 밖입니다.

## 완료 조건과 근거

허용 tenant·행동·profile을 서버 정책으로 확인하고 비허용 자료를 읽지 않습니다. 정책/연결 변경의 거부·회수·격리·보존과 신규 무소속 가입·기존 pending 복구를 확인합니다. 실제 운영 반영과 합성 시안을 구분합니다.
