## 2026-10-31 — 문서 목록과 상세를 중심으로 기본 Layout 검토

색상은 사용자가 선택한 [D-086의 연속된 작업 면](DECISIONS.md#d-086--연속된-작업-면을-기준으로-색상-구성-선택-2026-10-31)을 기준으로 한다. AI 채팅·온톨로지의 기존 참고 방향은 유지하고, 일반 목록·읽기 상세·원본·편집·이력·폼·설정·진행 화면의 기본 배치를 검토했다. 아래는 Layout 제안이며 제품 반영이나 사용자 선택 완료가 아니다.

### Layout을 결정하는 공통 원칙

- 외곽 메뉴와 상단 프레임은 유지하고, 페이지는 **대상 제목·주행동 → 찾기/전환 도구 → 실제 내용** 순서로 읽히게 한다. 같은 앱 제목/화면 제목/안내를 반복해 첫 내용을 밀어내지 않는다.
- 페이지 제목·도구줄·주내용의 왼쪽 출발선을 맞춘다. 좁은 본문/폼은 주 작업 영역 안에서 균형 있게 배치하며 오른쪽 공백을 상시 빈 패널로 채우지 않는다.
- 일반 목록은 가용 폭을 활용한다. 문서의 읽기 본문만 대략680~800px, 일반 입력 폼은640~800px를 시작값으로 검토한다. 이는 기준안이며 모든 화면에 같은 최대 폭을 강제하거나 실측 완료한 값이 아니다.
- 한 항목 안의 다른 내용을 여는 본문/원본/이력/AI 작업은 탭이고, 같은 목록을 좁히는 상태/형식은 필터다. 두 역할의 위치와 모양을 구분한다.
- 주행동은 해당 제목/작업 영역 가까이에 둔다. 읽기 화면의 편집, 편집기의 변경 확인/저장, 선택 판본의 복원을 같은 전역 행동줄에 무조건 합치지 않는다.
- 속성은 보조영역 한 곳으로 모으고, 본문을 읽기 어려워질 때 보조영역을 접거나 본문 뒤로 이동한다. 좁은 화면에서 보조 정보가 본문보다 먼저 길게 나오는 현재 규칙을 바꿀 필요가 있다.
- 일반 목록/읽기/설정은 세로 스크롤의 주체를 명확히 한다. 독립적으로 탐색해야 하는 이력 목록+비교는 패널별 스크롤을 검토하되, 외곽/내부 이중 스크롤이 실제로 발생하는지는 후속 런타임 확인이 필요하다.

### 문서 목록

권장 순서: **문서 제목·등록 → 검색·추출 상태·파일 형식 → 문서 표 → 페이지 이동**.

- 현재 상태 필터·검색 도구·범위 안내·결과 건수가 여러 줄로 나뉘고 실제 표가 늦게 시작한다. 찾기 도구를 같은 영역에 묶고 적용 범위/건수는 한 줄의 보조 정보로 정리한다.
- 기본 열은 문서 이름 / 추출 상태 / 관계 / 문서 종류. 문서 이름이 주진입이고 관계 건수는 그래프 진입이다. 별도 큰 열기 버튼의 반복 대신 제목 링크의 의미를 명확히 하는 방향을 검토한다.
- 제목 아래의 작성 경로 미기록·고정 형식 설명 같은 반복 문장을 줄이고 실제 구별에 필요한 보조 정보만 두 번째 줄에 둔다. 목록에는 현재 제공되지 않는 작성일/수정일을 만들지 않는다.
- 목록 기본 상태에 상세 패널을 미리 예약하지 않는다. 문서 읽기는 별도 상세 경로로 이동하고, 돌아올 때 검색/필터/페이지/위치 보존을 검증한다. 미리보기 패널은 현재 지원 기능으로 가정하지 않는다.
- 좁은 폭에서는 제목/상태를 우선하고 보조 열을 재배치한다. 기능이 없는 체크박스·정렬·일괄 행동을 디자인 장식으로 추가하지 않는다.

근거: `DocumentLibrary.tsx:145,155,180,242,320,328,385`와 `DocumentLibrary.module.scss:64,95,168,186,224`. 상태/파일 형식 필터는 현재 불러온 범위에 적용되므로 이 제한을 숨기거나 서버 전체 검색 필터처럼 표현하지 않는다.

### Wiki 읽기 상세와 원본 상세

권장 순서: **문서 목록으로 돌아가기 → 제목·본문 편집 → 본문/원본/이력/AI 작업 → 본문 + 보조 속성**.

- 본문을 첫 번째 주요 정보로 둔다. 현재 본문 앞의 설명·태그와 오른쪽 파일 속성이 분산되어 있으므로 하나의 속성 영역에 모은다. 앱이 추가하는 문서 제목은 한 번으로 정리하되 원문 본문 안의 제목은 임의 삭제하지 않는다.
- 본문은 읽기 폭을 제한하고, 속성/관계 상태/관련 행동은 오른쪽의 작은 보조영역으로 둔다. 단일 본문일 때는 작업 영역 안에서 중심을 맞추며, 보조영역이 있으면 본문+보조영역 전체의 균형을 맞춘다.
- Attio의 속성 정돈 원칙을 사용하되, 왼쪽 속성을 첫 시선에 두는 CRM 배치를 Wiki에 그대로 적용하지 않는다. 우리 화면에서는 본문 읽기가 우선이다.
- 보조영역의 관계 재추출·이 문서로 질문·새로 읽기는 해당 상태와 가까이 둔다. 설명·태그·형식·크기·원본과 기술 참조는 역할별로 묶고 기술 정보는 기존 펼침을 유지한다.
- 원본 상세는 **제목 → 판본 선택·다운로드 → 원문 미리보기**가 주영역이다. 현재 원문 앞의 긴 판본/파일 정보와 떨어진 다운로드를 정리하고, 파생 Wiki는 보조영역에 둔다. 미지원 형식과 읽기 실패의 대안 행동은 유지한다.
- 좁아지면 속성을 본문 뒤의 접는 영역으로 옮긴다. 본문과 선택 판본을 유지하며, 모든 속성을 먼저 펼쳐 본문을 아래로 밀지 않는다.

## 2026-10-31 — 전체 색상 구성과 WCAG 기준 검토

후속 사용자 선택: 비교 시안의 1번 **‘연속된 작업 면 · 제안’**을 선택했다. [D-086](DECISIONS.md#d-086--연속된-작업-면을-기준으로-색상-구성-선택-2026-10-31)에 기록했다. 아래는 선택 전 조사와 시작 팔레트이며 제품 적용·전체 레이아웃 확정과 구분한다.

사용자는 흰 페이지 중간의 회색 탭과 그 아래 반복되는 별도 배경을 예로 들며, 화면 전체가 조각나 보이는 문제를 지적했다. 이번 범위는 색상 구성의 검토·제안이며 제품 색상/컴포넌트를 변경하거나 디자인을 확정한 것이 아니다. 기존 실제 제품 캡처와 현재 스타일·색상 원본을 대조했고 W3C 공식 WCAG 2.2 문서를 확인했다.

### 현재 색상 구성의 문제

1. **공간의 역할보다 구현 조각마다 배경이 생긴다.** 문서는 흰 페이지 → 회색 필터 띠 → 흰 도구줄(회색 검색 포함) → 회색 표 머리 → 흰 목록으로 이어진다. 등록도 회색 탭과 회색 업로드 영역이 따로 놓인다. 색 차이가 작아도 넓은 띠가 반복되면 작업 흐름을 가로지르는 경계가 된다.
2. **같은 회색이 너무 많은 역할을 맡는다.** `surface.panel`은 사이드바·탭·검색·표 머리·업로드·원문/코드·보조 버튼에 함께 사용된다. 공간 구분, 입력 가능 여부, 보조 정보의 의미가 분리되지 않는다.
3. **선택·hover·안내의 색이 섞인다.** 문서 행의 hover와 선택이 같은 파란 면이고, 채팅은 선택된 대화의 파란 면을 hover 회색이 덮는다. 같은 파란 면을 정보 안내·초안에도 사용해 현재 선택의 의미가 약해진다.
4. **배경과 경계선이 겹쳐 구획을 중복 강조한다.** 앱 영역·섹션·표 행·입력·코드 상자에 같은 `border.default`가 쓰인다. 회색 면+외곽선+내부 구분선이 중첩되지만 중요한 입력 경계 자체의 대비는 낮다.
5. **보조 내용을 매번 색 상자로 만든다.** 일반 설명·원문·후보·안내가 각각 회색/파란 상자로 둘러싸인다. 사용자가 조치해야 하는 상태와 읽기용 정보가 비슷한 면적의 강조를 받는다.
6. **상태 변화에서 문자 대비가 떨어진다.** 기본 글자색은 대체로 충분하지만 버튼 전체의 밝기/투명도 변경은 글자까지 바꾼다. 기본 상태의 색상표만 검증해서는 발견되지 않는다.

근거: `DocumentLibrary.module.scss`의 필터64·검색111·표 머리190·hover216·선택589, `ImportDocumentContent.module.scss`의 탭10·업로드78·hover165·안내196, `KnowledgeChat.module.scss`의 선택468·hover571, `LineComparison.module.scss`, `StatusNotice.module.scss`, `app/design/tokens.json`. 공통 Tabs와 WorkspaceSection의 기본 배경은 이미 투명하므로 회색 탭이 모든 공통 구현의 필수 규칙인 것은 아니다.

### 권장하는 색의 역할

**주 작업은 하나의 연속된 면으로 유지하고, 색은 공간의 큰 경계·조작 상태·업무상 의미에 제한한다.** 모든 요소를 무조건 같은 색으로 합치거나 모든 테두리를 제거하는 제안이 아니다.

| 대상 | 제안 |
| --- | --- |
| 앱 탐색 공간 | 사이드바 같은 전역 영역에만 옅은 중립색. 본문 안의 모든 하위 패널에 이 색을 반복하지 않음. |
| 페이지·제목줄·중간 탭·도구줄 | 같은 바탕을 이어 사용. 제목/간격/위치로 위계를 먼저 만들고 필요한 구분선만 남김. |
| 탭·필터 | 넓은 회색 받침 제거. 활성 항목 아래 선과 글자 굵기로 선택을 표시. 필터의 개별 선택은 작은 중립/선택 표시로 제한. |
| 일반 목록·표 | 기본 행과 표 머리는 같은 바탕. 머리의 글자 위계와 아래선, 필요한 행 구분선으로 정렬을 읽게 함. 항상 줄무늬 배경을 추가하지 않음. |
| 하위 섹션·속성·원문 인용 | 주변 바탕 유지. 간격·제목·출처와 필요한 세로선으로 구별. 별도 스크롤/작업 경계가 있는 패널은 한 경계로 표현. |
| 입력 | 활성 입력의 바탕은 같은 규칙으로 사용. 읽기 전용/비활성은 상태를 명시. 식별에 필요한 입력 경계는 장식용 구분선과 다른 대비 기준 사용. |
| hover·선택·포커스 | hover는 옅은 중립색, 선택은 작은 파란 표시+옅은 파란 면, 키보드 포커스는 명확한 외곽선. 선택+hover에서도 선택 표시 보존. |
| 행동 버튼 | 주요 행동에 파란 채움. 보조 행동은 중립/투명. hover에는 전용 배경색을 사용하고 활성 버튼 전체의 opacity/filter로 글자까지 바꾸지 않음. |
| 상태·안내 | 성공/주의/오류는 문구·아이콘과 작은 영역에 사용. 넓은 상태색 면은 조치가 필요한 안내에 제한. 정상 설명은 본문에 통합. |
| 팝오버·대화상자 | 실제로 위에 떠 있는 면만 별도 배경과 필요한 그림자. 본문 안의 구획에 같은 부상 표현을 반복하지 않음. |
| 그래프·변경 비교 | 출처별 관계색·선 종류·범례와 추가/삭제의 의미 보존. 일반 앱의 선택 강조와 업무 의미 색을 전역 치환으로 합치지 않음. |

### 시작 팔레트 제안 — 미확정

기존 중립 문자색과 파란 강조를 유지하면서 면과 경계의 역할을 나눈다. 새 토큰 값으로 반영한 것은 아니다.

| 역할 | 밝음 | 어두움 |
| --- | --- | --- |
| 주 작업 면 | `#FFFFFF` | `#1F1F1F` |
| 앱 탐색 면 | `#F7F7F8` | `#191A1C` |
| 본문 / 보조 문자 | `#333333` / `#616161` | `#CCCCCC` / `#9D9D9D` |
| 장식·내용 구분선 | `#E5E7EB` | `#3A3D42` |
| 식별에 필요한 입력 경계 | `#858B94` | `#828A96` |
| hover | `#F2F3F5` | `#2A2D32` |
| 선택 면 / 선택 표시 | `#EAF2FB` / `#005FB8` | `#22364B` / `#4DAAFC` |
| 주요 버튼 배경 / 문자 | `#005FB8` / `#FFFFFF` | `#2563A6` / `#FFFFFF` |

이 후보의 계산상 대비는 주요 버튼 글자 6.308/6.151, 입력 경계/작업 면 3.433/4.729, 선택 표시/선택 면 5.585/4.991이다. 밝은 입력 경계는 탐색 면 위에서도 3.206이다. 구분선은 장식용이며 이 값으로 입력 경계를 다시 대체하지 않는다. 다크 테마는 단순 반전 대신 같은 역할을 별도 조합으로 검증한다.

### W3C 기준과 디자인 판단의 구분

W3C의 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)는 접근성 기준이며 특정 배색이나 모든 패널의 배경 차이를 지정하는 미감 규칙은 아니다. 본 제품은 **AA를 검증 목표로 삼는 방향을 제안**하며, 이번 계산만으로 앱 전체 적합성을 선언하지 않는다.

- [1.4.3 Contrast (Minimum), AA](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html): 일반 문자 4.5:1 이상, 큰 문자 3:1 이상. 큰 문자는 통상 24 CSS px 또는 약18.67px 굵은 글자에 해당하며 현재 12~14px UI는 일반 문자 기준을 적용한다. 보조문·placeholder·hover 때의 문자도 확인한다. 임계값 판정 전 반올림하지 않는다.
- [1.4.11 Non-text Contrast, AA](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html): 컨트롤/상태를 식별하는 데 필요한 시각 정보와 의미 있는 그래픽은 인접색 대비 3:1 이상. 모든 카드·면·장식선에 3:1이 필요한 것은 아니다. 선택의 옅은 배경만 낮은 대비라고 실패 판정하지 않고, 함께 있는 선/체크 등 실제 식별 수단을 확인한다. 서로 동시에 인접하지 않는 기본색/hover색 자체 사이에 3:1을 요구하는 규칙도 아니다.
- [1.4.1 Use of Color, A](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html): 색만으로 정보·행동·상태를 전달하지 않는다. 선택에는 선/체크/굵기, 오류에는 아이콘/문구, 그래프에는 선 형태/범례/이름을 함께 사용한다.
- [2.4.11 Focus Not Obscured (Minimum), AA](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html): 키보드 초점을 받은 요소가 제작한 다른 콘텐츠에 완전히 가려지지 않아야 한다. 색 대비만으로 포커스 사용성을 대체하지 않는다.
- [2.4.13 Focus Appearance, AAA](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html): 초점 표시의 면적과 상태 간 대비에 관한 상위 기준. 2 CSS px 둘레 상당 면적과 같은 픽셀의 초점 전후 3:1을 참고할 수 있지만 **AA 의무 규칙으로 오기하지 않는다.**

### 검토용 시안과 남은 범위

기존 문서 화면에서 관찰한 색 배치 패턴과 제안 방향을 동일한 예시 내용으로 비교하는 대화 내 시안을 작성했다. **실제 제품 캡처나 기능 구현 결과가 아니다.** 전체 레이아웃 승인안으로 취급하지 않는다. 라이트/다크, 두 구성 전환, 필터·검색·선택 상세를 국소적으로 비교한다. 파일은 작업 대화의 `wiki-color-surfaces.html`이며 제품 소스와 분리했다.

후속 구현에서는 공통 색상 역할 확정 → 화면별 개별 배경 정리 → 상태 조합 대비 확인 순서로 진행한다. 모든 활성 화면·정상/hover/selected/focus/error·밝음/어두움에서 연속된 면과 의미가 유지되는지 비교해야 한다. 이번에는 제품 코드·토큰·운영 자료를 변경하지 않았다.

## 2026-10-31 — 가장 기본적인 Base UI 문제 도출

목표는 특정 Select 수정이나 화면별 정보 구조 재설계가 아니라, 모든 화면의 바탕이 되는 **치수·여백·정렬·문자·상태 표현의 결함**을 찾는 것이다. 제품 소스는 변경하지 않았다. 아래 개선 기준은 후속 구현을 위한 제안이며 적용 완료나 신규 디자인 결정이 아니다.

근거는 현재 제품의 격리 웹 실행(1280×720)과 공통/화면별 스타일의 실제 적용 순서다. 로그인·설정·문서·추출안 준비·검토함·채팅의 계산된 치수와 키보드 포커스를 측정했다. `실측`은 브라우저에서 재현한 것, `코드`는 구현 근거는 확인했지만 해당 상태를 화면에서 재현하지 않은 것이다. 서로 다른 역할의 요소가 다르다는 이유만으로 결함으로 취급하지 않는다.

### 근본 원인과 우선순위

1. **기본 요소의 완성된 규격 대신 일부 속성만 공유한다.** 치수·문자·아이콘·상태가 함께 묶이지 않아 조합하면 달라진다. B01~B06을 먼저 정리할 필요가 있다.
2. **전역 기본값, 공통 컴포넌트, 화면별 예외의 우선순위가 뒤섞였다.** 작은 버튼 옵션이 무효화되고, 목록용 포커스가 일반 버튼까지 적용된다. 값만 추가로 덮는 수정으로는 반복될 가능성이 높다.
3. **정상 상태 외의 기본 동작이 덜 정리됐다.** B07~B10의 선택·포커스·비활성·오류를 같은 요소의 상태 묶음으로 확인해야 한다.
4. **컴포넌트를 배치하는 규칙도 공통 UI의 일부다.** B11~B12와 행/속성 정렬을 화면마다 독립 조정하면 컨트롤을 교체해도 들쭉날쭉한 인상이 남는다.

### 오진에서 제외한 항목과 확인 범위

- 현재 일반 Select는 텍스트 왼쪽 12px, 화살표 박스 오른쪽 12px, 오른쪽 예약 영역 36px, 높이 36px다. 문서 화면에 남은 10px/11px 설정은 최종 적용에서 덮이므로 현재 결함으로 집계하지 않는다. 글리프 자체의 안쪽 여백과 아이콘 박스의 여백도 구분한다.
- 검색 입력의 내부 34px는 외곽 테두리를 합치면 36px이므로 높이 결함이 아니다. 숨긴 1px 라디오도 접근성 구현으로, 시각 요소로 집계하지 않는다.
- 기본 Lucide 아이콘은 16px/선 두께1.75로 공유하고 색상은 의미별 변수를 사용한다. 모든 아이콘·다크 테마가 잘못됐다고 볼 근거는 없다. 색 대비 수치와 모든 긴 문자열/좁은 폭 상태를 이번에 새로 검증한 것은 아니다.
- 공유 Button의 포커스 offset4 및 Tabs의 offset-2 선언만으로 실제 결과를 단정하지 않았다. 최종 적용과 실제 키보드 포커스를 기준으로 B08을 작성했다.
- 오류·비활성 hover·체크박스·일부 반응형 항목은 코드 근거이며 해당 상태의 런타임 재현은 후속 확인 대상이다. 실제 AI 실행·저장·운영 자료 변경은 수행하지 않았다.

## 2026-10-31 — 화면보다 작은 작업 단위로 다시 판단

사용자는 앞선 디자인이 부분적으로만 적용되고, 레퍼런스의 목적·정보 위계가 반영되지 않았으며, 조작 위치와 움직이는 패널이 어긋나고 불필요한 설명이 많다고 지적했다. 상위 메뉴만으로 묶은 개선안을 다시 세분화한다. 아래는 현재 구현의 탭·선택·작업 상태를 읽은 **설계 제안**이다. 신규 메뉴 목록이나 구현 완료 보고가 아니다.

근거 범위: 앞선 격리 화면의 캡처와 이번 활성 12개 경로의 소스 감사. 아래 모든 예외 상태를 실제로 재현한 것은 아니다. 이번 중간 UI 수정은 작성자가 이번 변경분만 복원했고 문서·등록·검토함의 타입/형식 검사를 통과했다. 앞선 작동 소스는 유지한다.

### 제품의 작업 흐름과 현재 문제

자료 등록 → 문서 읽기 → 개념·관계 이해 → 원문/전문가 판단 → 질문·산출물 활용을 중심으로 삼는다. 세션과 분석 작업은 이 흐름의 진행 상태를 확인하는 지원 화면이다.

1. 모든 페이지가 제목·설명·상태·버튼을 세로로 나열해 읽기/탐색/판단/작성/진행 확인의 차이가 사라졌다.
2. 전역 현재 화면 이름과 페이지 제목, 섹션 제목과 설명, 선택 제목과 인용이 반복된다.
3. 대상·근거·현재 상태·다음 행동이 떨어져 있다. 기술 기록과 정상 처리 설명이 핵심 정보보다 먼저 나온다.
4. 공통 컨트롤만 바꿔도 화면별 헤더·도구줄·간격이 남아 적용 수준이 달라진다.
5. 패널 제어 위치뿐 아니라 선택 맥락에도 문제가 있다. 검토함에서 특정 주장으로 진입할 때 그래프는 첫 개념, 상세는 해당 주장일 수 있다.

### 구현 전 확인 기준

- 각 단위마다 대상 제목, 주요 정보, 주행동, 보조 정보의 위치를 정한 뒤 실제 컴포넌트로 표현한다.

## 공통 개선 기준과 유지할 동작

패널마다 사용자가 아래 순서로 찾을 수 있게 합니다. 모든 항목을 별도 카드로 감싸는 대신 구역 제목, 간격, 얇은 경계와 짧은 상태 요약으로 구분합니다.

1. **현재 대상**: 이름, 선택 항목, 현재 위치.
2. **핵심 내용**: 본문 또는 관계의 의미.
3. **조건과 근거**: 적용 범위, 원문 인용, 출처.
4. **현재 상태와 다음 행동**: 미저장·미적용·검토 필요와 관련 버튼.
5. **상세 정보**: 긴 판본값, 식별자, 기술 정보는 필요할 때 펼칩니다.

이미 있는 문서 탭·정보 사이드바, 설명 fieldset, 등록 결과의 단계별 목록, 명시 참조와 후보의 구분, 빈 상태와 조회 실패 구분, 메뉴·탭 선택 표시를 보존해야 합니다. 온톨로지의 직각 연결선과 너비별 패널 전환도 유지합니다.

AI 채팅은 반환 파일이 없을 때 상시 파일 영역을 추가하지 않습니다. 현재 소스에는 반환 파일 패널 자체가 없고 답변 인용 창과 수동 산출물 생성 흐름이 있습니다. 이 둘을 반환 파일 패널로 간주하거나 조건이 구현·검증됐다고 기록하면 안 됩니다.
