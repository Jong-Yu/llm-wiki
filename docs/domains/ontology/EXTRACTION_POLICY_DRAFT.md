# 온톨로지 추출 정책 초안

2026-10-29 · [D-077](DECISIONS.md#d-077--명시-내용-보존과-추정-검토의-추출-정책-초안-2026-10-29)

**상태: 합의한 추출 정책을 의미 프롬프트 원본과 개발 예시에 반영했습니다.** 구조 검사와 격리된 실제 모델 평가의 결과는 [HISTORY](HISTORY.md)에 기록합니다. 운영 발행본·기존 고정 작업은 자동으로 변경되지 않으며, 서버/UI가 필요한 항목은 마지막 대조표에 구분합니다. 필수 요구를 지침에 적었다는 사실만으로 품질 달성을 선언하지 않습니다.

외부 MCP 비교 후 추가한 [개선 조사안](#외부-mcp의-장점을-흡수할-개선-조사안)은 기존 EP/RP와 구분합니다. 최신 구현은 아래 [IMP01·제한된 IMP02 적용](#imp01제한된-imp02-적용)을 따릅니다. 이전 [후보별 새 비정형 표본의 판단](#후보별-새-비정형-표본의-최신-판단), [1~3번 판단](#세-후보의-분리-검증과-적용-판단), [4~7번 판단](#후속-네-후보의-분리-검증과-적용-판단)도 당시 근거로 보존합니다.

목표는 다양한 분야의 원문에 명시된 내용을 충실히 보존하고, AI의 추정은 전문가가 검토할 수 있게 남기는 것입니다. 같은 입력에서는 개체·관계·속성·조건과 추정 후보가 의미적으로 일관되어야 합니다. 기존 개체·관계·속성·한정어·출처 구조를 유지하며 사례마다 새 필드를 추가하지 않습니다.

## 공통 MUST의 구현 대조와 검증 상태

IMP01/02 후속에서 EP01~11·RP01~04의 지침 존재, 자동 검사, 의미 검토, 실제 검토 항목 연결을 대조했습니다. [통합 보고서의 대조표](../../../evals/2026-10-29-must-integration/REPORT.md)에 항목별 근거와 미구현 범위를 기록합니다. 새7개+기존 설정 회귀1개를 통과했고, 원문·계획/조건·수치 원형·후보 이유/질문과 미검토 상태, 위조 승인 거부·원시 실패 보존을 확인했습니다.

D-076의 허용된 과거 검토 이력 제외는 조립 감사/경고로, 실제 원문·현재 근거 미독은 차단 대상으로 구분하는 안내를 추가했습니다. 새 보고 정책/템플릿은 실행 지문에 포함하고 기존 모델 보고를 사후 고치지 않습니다. full 입력은 변경 전과 동일합니다.

새 합성 원문의 최종3개에서 중요 누락은 없었고 축약 반복의 후보 명제·이유·질문 의미는 같았지만, 실제 관계 구성 차이가 남아 EP10 전체 일관성 달성으로 표시하지 않습니다. 전체 입력의 발화 귀속 확대도 기록했습니다. 진단은 계속 분석 결과에 보존되며, 누락/표현 한계/충돌을 각각 전문가 검토함 항목으로 만들고 해결하는 RP03 연결은 아직 없습니다. 이 점검 완료를 모든 MUST의 의미적 달성이나 운영 적용 완료로 해석하지 않습니다.

## IMP01·제한된 IMP02 적용

사용자 확정에 따라 IMP01의 순수 검사/MCP 진단/최대2회 전체 재추출을 구현하고 IMP02는 방향·끝점 역할 지침만 추가했습니다. 코드와 규약 원본의 범위는 [D-081](DECISIONS.md#d-081--저장-없는-초안-검사와-제한된-끝점-역할-규칙-2026-10-29), 새 원문 비교와 실패 보존은 [보고서](../../../evals/2026-10-29-adopt-imp01-02/REPORT.md)에 둡니다. 형식 통과는 의미 검증이나 저장 승인이 아닙니다. 기존 운영 릴리스/고정 작업은 유지하며 새 규약 발행은 별도입니다.

새 비교는 핵심 내용32/32 동률, 완전한 질문 구조화9/30→7/30, 개별 관계 요소22/56→23/56으로 엇갈렸고 IMP02 쪽에 원문 미지원 관계1개가 있었습니다. 따라서 제한된 지침의 구현과 검증은 완료했지만 의미 개선 확정으로 표시하지 않습니다. IMP01은 인용 오류4건을 각1회 수정했으며 최종8건 모두 저장에 통과했습니다. 수정 중 조건 범위의 모호함1건이 남아 자동 의미 보장은 하지 않습니다.

IMP05 별도 시간 장부·조회 엔진은 사용자 결정으로 도입 대상에서 제외했습니다([D-084](DECISIONS.md#d-084--imp05-별도-시간-장부와-조회-엔진의-도입-제외-2026-10-30)). 후속 개발·재검증도 현재 범위에 두지 않습니다. 초기 장부 제공 시험의24/24 동률·약2.44배 비용은 당시 기록이며, 최신 평가 근거는 [구현 개선 뒤 새 표본 비교](../../../evals/2026-10-30-temporal-query-v2/REPORT.md)입니다. 새 표본의 공통 완료2문서에서 수정 전/후 엔진0/28→18/28·최종 답변9/56→48/56으로 개선됐지만 기존 방식56/56보다 낮고 토큰은1.63배입니다. 전체3문서 중1문서는 두 장부 방식 모두 생성 검증에 실패했으며 예정 분모와 비용에 남겼습니다. 기존 그래프 방식·시간 정보 보존·IMP01·제한된 IMP02는 유지합니다. 구현 개선과 장부 일반의 유효성, 기본 도입의 효용을 구분하며 평가 자료를 보존합니다. 다른 후보는 이번 적용 범위에 넣지 않습니다.

## 요구 수준과 책임

- **MUST / MUST NOT**: 필수 요구 / 금지입니다. 위반을 발견하면 해당 항목을 준수로 표시하지 않습니다.
- **SHOULD**: 기본 권고입니다. 달리 처리할 타당한 이유와 영향을 남깁니다.
- **MAY**: 사용자가 선택할 수 있는 동작입니다.

용어의 강도는 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119.html)와 [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174.html)를 따릅니다. MUST는 자동 보장의 선언이 아닙니다. 형식·인용·판본은 코드로 검사하고, 원문 지지·누락·추론·충돌 의미는 별도 검토합니다. 서버의 자동 검사 통과와 전문가의 판단을 구분합니다.

아래 EP/RP 식별자는 이 초안의 항목 번호입니다. 현재 발행 규약의 R-A/R-S Rule ID나 API enum을 추가·변경하지 않습니다. 기존 규칙별 검사 계약은 [analysis 결정](../analysis/DECISIONS.md#rule-분류검증위반-처리-2026-10-25)을 참조합니다.

## 내용과 검토 상태의 구분

‘원문에 명시됨’은 문서가 그 주장을 한다는 뜻이며, 현실에서 참임을 인증한 것이 아닙니다. 계획·가능성·부정·규범은 원문이 말하는 내용의 성격이고, AI 추정·전문가 판단은 해석의 근거와 검토 출처입니다. 서로 다른 축으로 보존합니다.

| 구분 | 보존할 내용 | 처리 원칙 |
| --- | --- | --- |
| 원문에 명시된 주장 | 대상·관계·속성·조건·시점·발화자와 인용 | 원문이 말한 상태 그대로 추출 |
| AI 추정 | 제안한 연결, 실제 전제와 가정, 불확실한 이유, 확인 질문 | 근거 관계와 분리하고 전문가 판단 전 확정 사실로 사용하지 않음 |
| 표현 한계 | 원문 주장과 위치, 표현할 수 없는 의미, 검토 질문 | 부정확한 관계를 만들지 않고 연결을 보류 |
| 원문 간 충돌 | 양쪽 주장·근거와 각각의 적용 범위·시점 | 한쪽을 임의로 버리지 않고 충돌 검토 대상으로 제시 |

이 표는 정책상의 구분입니다. 현재 API가 이 네 가지를 모두 같은 검토함에서 처리한다는 뜻은 아닙니다.

## 추출 필수 규칙

### EP-01 명시된 내용 보존

**MUST:** 선택한 원문에서 현재 구조로 표현할 수 있는 명시적 개체·관계·속성·조건을 보존합니다. AI의 중요도 판단이나 사용자의 조회 관점으로 추출 범위를 줄이지 않습니다. 표·주석·조건·예외도 선택 범위에 포함되면 함께 읽습니다. 여러 분야가 섞여 있어도 주장별로 해석합니다.

**MUST:** 미독·표현 한계·출력 한도 때문에 담지 못한 내용은 원문 위치, 잃는 의미와 이유를 남깁니다. 진단이나 인용에만 남긴 내용을 구조화에 성공한 것으로 세지 않습니다. 입력을 조용히 자르거나 문서/출력 한도를 넘겨 제출하지 않습니다. 한도를 초과하는 범위는 불완전함을 드러내고 범위 조정을 요청합니다.

### EP-02 넓은 추정 제안과 근거 분리

**MUST:** 원문에 직접 없는 연결도 검토 가능한 추정 후보로 넓게 제안할 수 있도록 하되, 전제·가정·불확실한 이유와 구체적인 확인 질문을 붙입니다. 실제 인용이 있다는 사실만으로 그 인용이 추정의 결론을 입증한다고 주장하지 않습니다.

**MUST NOT:** 추정 결론을 근거 관계로 확정하거나, 가상의 개체·인용·사용자 승인을 만들어 저장합니다. 현재 제출 스키마가 허용하는 끝점과 술어만 후보에 사용합니다. 후보 형식으로도 표현할 수 없는 내용은 EP-08로 보냅니다. 명시된 주장을 전부 후보로 내려 정확성 점수를 높이지 않습니다.

‘넓게’는 임의의 모든 조합을 생성한다는 뜻이 아닙니다. 첫 구현에서는 원문 순서로 지시 대상/동일성의 모호함, 명시 규칙의 특정 대상 적용 미확인, 같은 작업에 서술된 주체·단계의 빠진 연결을 모두 점검합니다. 원문 전제와 확인할 가정을 특정하고, 허용 끝점·술어로 전문가가 확인/반박할 수 있는 후보만 남깁니다. 이는 평가 가능한 첫 선정 절차이며 모든 유용한 추론을 포괄한다는 주장이 아닙니다. 후보 개수 제한, 모든 쌍·추이·역관계의 자동 생성은 추가하지 않습니다.

### EP-03 계획과 조건 보존

**MUST:** 원문의 부정·가능성·능력·계획·가정, 조건·예외·범위·시점을 해당 주장에 붙입니다. 기존 qualifiers의 다섯 키를 명시하고, 조건 문자열은 원문에 근거해야 합니다. 모델 자신의 자신감으로 원문의 양태를 바꾸지 않습니다.

‘민수는 내년에 담당할 예정이다’는 계획·시점을 가진 원문 주장입니다. AI가 새로 추론한 후보와 구별합니다. ‘A는 평일에 B를, 주말에 C를 사용한다’는 조건별 관계로 보존합니다. 다른 조건·기간의 관계를 같은 것으로 합치지 않습니다.

### EP-04 규약과 실제 행동 구분

**MUST:** 의무·금지·권고·허용을 규범으로 보존합니다. ‘해서는 안 된다’를 실제로 하지 않았다는 사실로, ‘해야 한다’를 실제 수행한 사실로 바꾸지 않습니다.

현재 구조에서는 적용 대상·행위·규범 강도·조건·예외를 포함하는 연속 규범 문장을 텍스트 속성으로 보존합니다. 속성명·값·인용·길이 제약을 충족해야 하며, 충족할 수 없는 부분은 표현 한계로 남깁니다. 텍스트 보존을 실행 가능한 규범 논리나 준수 확인으로 표시하지 않습니다. 구체적인 저장 기준은 [D-062](DECISIONS.md#d-062--규범-문장의-텍스트-보존과-사실-관계-구분-2026-10-26)를 유지합니다.

### EP-05 대상의 동일성과 이름

**MUST:** 원문이 ‘주문 관리 시스템(OMS)’처럼 동일 대상의 이름·약어임을 명시하면 문서 안에서 같은 대상으로 연결합니다. 종류와 특정 개체, 업무 관점과 서로 다른 실체를 구별합니다.

**MUST NOT:** 이름·코드·문구가 같다는 이유만으로 다른 문서의 대상을 합치거나, 넓은 범주와 좁은 범주를 같은 ID로 처리합니다. 추정한 동일성은 검토 후보로 두고 문서·대상·근거 참조를 유지합니다. 비교 결과만으로 기존 판단을 자동 승계하지 않습니다.

### EP-06 관계와 과정 노드의 선택

**MUST:** 관계만으로 원문 의미를 담을 수 있으면 그 관계를 기본 표현으로 사용합니다. 행동 자체의 단계·담당·선후관계·입출력을 연결해야 할 때는 원문에 근거한 과정 노드를 사용합니다. 단순히 동사가 나온다는 이유로 매번 과정 노드를 추가하지 않습니다.

‘민수가 보고서를 작성했다’는 보고서의 작성자를 연결합니다. ‘보고서 작성은 자료 수집과 초안 작성으로 구성되며 각각 담당자가 있다’는 과정과 단계별 담당 관계를 표현합니다. 과정 노드의 존재를 실제 실행·완료의 증거로 취급하지 않습니다. 원문에 없는 과정 이름을 만들어 label 제약을 우회하지 않고, 실행에 고정된 스키마 버전의 관계만 사용합니다.

### EP-07 숫자와 단위의 원형 보존

**MUST:** 속성의 값·단위·근거는 원문 문자열로 보존합니다. 저장값을 계산·반올림·환산하거나 쉼표를 제거해 바꾸지 않습니다. 현 숫자 형식에 맞지 않는 표현은 허용되는 텍스트 속성으로 보존합니다.

비교에서는 같은 대상·통화/단위·기준 기간·조건·측정 기준·정밀도이고 환산이 명확할 때 ‘월 1만원’과 ‘월 10,000원’을 동치로 판별할 수 있습니다. 환산값은 비교용 파생값이며 원래 value/unit/evidence/revision을 대체하지 않습니다. 추가 가정이 필요하면 검토 대상으로 둡니다. 값의 동치는 관계 전체의 동일성·원문 동일성·claim ID 통합이나 승인 승계의 근거가 아닙니다.

### EP-08 지원하지 않는 관계의 연결 보류

**MUST:** 원문의 구체적인 관계를 현재 허용 술어로 충실히 표현할 수 없으면 그 연결을 보류합니다. 원문·위치·표현하려는 의미·한계·검토 질문을 보존하고 전문가 검토를 유도합니다.

**MUST NOT:** ‘A가 B를 대체한다’를 표현할 수 없다는 이유로 ‘관련 있음’이나 의미가 다른 술어로 약화해 연결합니다. `related_to`는 원문이 직접 일반 연관을 주장할 때만 사용합니다. 의미 프롬프트 원본에서 대체 사용 허용 예외를 제거했으며, 과거 발행본의 내용은 유지됩니다.

원문 문장은 가능한 경우 기존 텍스트 속성에 보존하되 개체·속성명·값·길이 제약을 지킵니다. 속성으로도 담을 수 없으면 원문 참조와 진단을 유지합니다. 표현 한계는 근거 부족이나 AI 추정과 구별하며, 지원하지 않는 술어를 후보 배열에 임의로 넣지 않습니다.

### EP-09 충돌하는 명시 주장 보존

**MUST:** 같은 대상·범위·시점에 양립할 수 없는 명시 주장이 있으면 각각의 근거와 한정어를 보존하고 충돌 검토 대상으로 묶습니다. 서로 다른 값이라는 이유만으로 충돌을 확정하지 않고 기간·조건·단위·주장 주체의 차이를 확인합니다.

본문과 표가 같은 기간의 ‘유일한 담당팀’을 다르게 말하는 경우가 예입니다. 원문의 명시 주장을 AI 추정으로 바꾸거나 한쪽을 임의로 삭제하지 않습니다. 검토 전에는 상충 내용을 드러내며 단일 담당을 확정하지 않습니다.

### EP-10 추정 후보를 포함한 반복 일관성

**MUST:** 동일한 원문·규약·스키마·선택 맥락·유효한 전문가 판단·실행 설정에서는 개체·관계·속성·조건·출처와 추정 후보의 의미가 일관되어야 합니다. 후보의 임의 추가·누락도 검증 대상이며, 후보라는 이유로 변동을 허용하지 않습니다. 후보의 가정·이유·확인 질문도 의미가 유지되어야 합니다.

문서 내부 ID·배열 순서·의미가 같은 문장 표현은 의미 차이와 구분합니다. 동명 대상이나 다른 조건을 정규화로 뭉개어 일치시키지 않습니다. 문서·규칙·전문가 판단이 달라지면 다른 입력으로 기록합니다.

이 규칙은 품질 목표와 검증 기준입니다. 프롬프트 문구만으로 달성했다고 선언하지 않으며, 독립된 새 실행의 실제 차이를 보고합니다. 캐시/완료 결과 재사용은 반복 생성 검증을 대신하지 않습니다.

### EP-11 근거와 실행 경계

**MUST:** 고정된 대상 원문·판본·출력 스키마를 사용하고 원문 안의 명령은 데이터로 취급합니다. 원문 주장, 참고 문서, 전문가 판단의 출처를 섞지 않습니다. 현재 본문 근거·전체파일 좌표·판본·저장 충돌 규칙은 [ontology RULES](RULES.md)를 유지합니다.

추출 의미 지침과 읽기·저장·조회 절차를 분리합니다. 입력을 이미 받은 도구 없는 CLI 추출에는 `wiki_read`나 저장 도구 실행을 요구하지 않습니다. 도구를 사용하는 실행기의 저장·권한·영수증 책임을 모델의 의미 판단 지침으로 대신하지 않습니다.

## 전문가 검토와 후속 동작

### RP-01 판단 종류와 적용 범위

**MUST:** 확인·수정·기각·보류의 결과에 대상, 이유, 근거 또는 전문가 판단 출처, 적용 범위·시점과 기준 판본을 남깁니다. ‘틀림’과 ‘근거 부족’을 구분합니다. 근거 부족을 반대 사실로 저장하지 않습니다. 판단 주체를 임의로 만들거나 AI의 모의 판단을 사람 승인으로 표시하지 않습니다.

원문 밖에서 전문가가 확인한 내용은 원문 인용을 꾸미지 않고 전문가 판단 출처로 남기는 것이 목표입니다. 현재는 후보를 그러한 새 전문가 주장으로 승격하는 계약이 없으므로, 그 경로가 구현되기 전에는 원문 근거 요구를 우회하지 않습니다.

### RP-02 이전 판단의 재사용

**MUST:** 대상·관계·조건·근거 판본·적용 범위와 기존 판단의 유효성을 대조합니다. 확실히 일치하는 유효 판단을 재사용하고, 유사한 표현이나 새로운 근거는 이전 판단과 차이를 보여주는 재검토 대상으로 둡니다.

현재 구현의 재추출 세대·원문/그래프/이력 변경에 따른 pending 경계를 유지합니다. 새 세대에 옛 승인·기각을 자동으로 옮기지 않습니다. 한 사례의 판단을 다른 대상이나 범위의 공통 규칙으로 확대하지 않습니다.

### RP-03 표현 한계와 충돌 검토

**MUST:** 표현 한계 검토에서는 기존 관계로 의미를 온전히 보존할 수 있는지, 새 관계 정의가 필요한지 판단하게 합니다. 새 관계가 필요하면 의미·방향·사용 기준과 스키마·검증기·규약 반영을 마친 뒤 연결합니다. 전문가의 문구 입력만으로 미지원 술어를 저장하지 않습니다.

**MUST:** 충돌 검토에서는 양쪽 근거를 비교해 맞는 관계를 선택하거나 수정·보류할 수 있게 합니다. 선택되지 않은 관계를 현재 사용하는 온톨로지에서 제거할 때도 원시 주장·근거·판단 이유·이력은 보존해 되돌릴 수 있게 합니다. 원문이 직접 반대 사실을 말했다는 의미로 기각을 변환하지 않습니다.

**MAY:** 사용자는 관계만 정리하거나 문서 수정안을 추가로 요청할 수 있습니다. 수정안 요청 시 AI 사용과 토큰 소비를 알리고, 변경 전후를 확인해 적용합니다. 저장 전 전체 문서 이력 보존·기준 판본 검사를 유지하며, 문서 변경 후 영향받은 관계와 과거 판단의 현재성을 다시 확인합니다. 그래프 검토와 문서 저장을 하나의 원자 동작으로 보장하는 계약은 아직 정하지 않았습니다.

### RP-04 정리와 비용 관리

**MUST:** 전문가의 명시 판단 저장이나 확실한 목록 정리를 위해 전체 그래프를 AI로 다시 해석하지 않습니다. Clean Up은 현재 사용 목록과 보존 이력을 구분하며, 근거 부족·미검토·과거라는 이유만으로 거짓을 만들거나 기록을 영구 삭제하지 않습니다. 실제 정리 가능 범위는 [D-075 공개 계약](PLAN.md#clean-up-공개-계약)을 따릅니다.

**SHOULD:** 검토 이유·질문은 전문가가 원문과 바로 대조할 수 있도록 짧고 구체적으로 작성합니다. 인용은 판단에 필요한 조건·예외·대명사 선행 문맥을 포함하며, 불필요하게 전체 본문을 각 주장에 반복하지 않습니다.

**MAY:** 공통 규칙 개선과 과거 문서 재검토는 사용자가 필요할 때 묶어서 요청합니다. AI가 반복 문제에서 규칙 개선안을 제안할 수 있으나 개별 판단과 공통 규칙 변경을 구분해 전문가가 적용 범위를 확인해야 합니다. 새 규약이 과거 작업을 자동 재추출하거나 이미 적용한 것으로 표시하게 하지 않습니다.

관련 자료·유효 판단만 필요한 시점에 전달하고 간결한 응답과 상세 조회를 구분합니다. 원문 조건을 잘라 비용을 낮추거나 일부 관계로 전체 그래프를 덮어쓰지 않습니다. 전송 크기·호출 수·추정치·실제 토큰 사용량은 구분합니다. 실제 구현 범위는 [D-076](../analysis/DECISIONS.md#d-076--명시-입력-보기와-검증된-재개로-분석-전송량-제한-2026-10-29)에 연결합니다.

## 확인할 결과와 검사 방식

| 확인 항목 | 검사 방식 | 통과로 대신할 수 없는 것 |
| --- | --- | --- |
| 구조·실제 인용·참조·판본·필수 키 | 기존 자동 검사와 격리 계약 검증 | 원문 의미의 정확성·사람 승인 |
| 명시된 주장과 조건의 정확성 | 원문에서 먼저 고정한 주장·확인 질문과 결과 대조 | 실제 인용이 포함되었다는 사실만으로 의미 지지 판정 |
| 누락과 표현 한계 | 선택 범위에서 표현 가능한 명시 주장과 미표현 내용을 각각 확인 | AI가 중요하다고 고른 일부만 확인하거나 진단만으로 보존 성공 처리 |
| 추정 후보의 적절성 | 실제 전제·가정·원문과의 구분, 검토 가능성을 별도 평가 | 모든 후보가 참이어야 한다는 채점 또는 후보 수만으로 품질 판정 |
| 반복 일관성 | 고정 입력의 새 실행들을 비교하고 후보까지 포함한 의미 차이 보고 | 캐시 재생, 임의 재시도로 같은 결과만 선택, ID만 비교 |
| 판단 지속성과 처리 비용 | 유효성·범위·이력·되돌림과 호출/전송량을 따로 확인 | 오래된 승인 자동 이식이나 바이트 감소를 실제 토큰 절감률로 표시 |

시험 원문은 미리 정한 한 분야에 한정하지 않습니다. 조건·예외, 과정·담당, 수치·표, 약어·모호함·충돌, 표현 한계를 포함하는 서로 다른 분야의 실제 원문으로 구성합니다. 사용자에게 자료 준비나 전체 채점을 요구하는 계획이 아닙니다.

개발 자료와 미사용 최종 검증 자료를 분리하고 [원문 분리 평가 규칙](EVALUATION.md)을 따릅니다. 후보의 이유·질문을 가리는 검증 입력 제한을 유지하고, 그 설명의 적절성은 판정 확정 후 별도로 검토합니다. 실제 의미 평가, 같은 모델의 제한, 전문가의 실제 참여 여부를 구별합니다. 초안의 예시는 설명용이며 독립 평가 결과가 아닙니다.

### IMP-01 저장 없는 초안 검사

현재 [CLI 어댑터](../../../core/client/ai/codex.py)는 JSON 스키마를 검사하고, [OntologyStore](../../../core/modules/ontology/store.py)는 실제 저장 직전에 구조·정확 인용·참조·판본을 검사한다. 반면 [분석 결과 저장의 save=false](../../../core/modules/analysis_results/store.py)는 현재 입력/권한/진단을 확인해 초안 영수증을 보존하지만 **그래프 검사는 생략한다**. 따라서 이를 기존의 완전한 dry-run 검증이라고 부르지 않는다. 별도 의미 검토는 [이미 구현된 분리 세션](../../../core/client/semantic_check.py)을 재사용하며 새 검사기로 중복 구현하지 않는다.

추가 후보는 고정 원문/스키마/판본으로 기존 그래프 검증기를 호출해, 위키·그래프·검토 원장·작업 상태를 바꾸지 않고 항목 경로/검사 종류/근거 위치를 반환하는 검사 동작이다. 현재의 첫 오류 반환 계약을 바꾸기보다 별도 명시 검사 계약을 설계한다. 오류 수·처리량은 제한하고 목록이 잘리면 불완전함을 표시한다. 검사 시점의 성공은 저장 허가가 아니므로 실제 저장에서 최신 권한·전체파일 revision·검토 상태 CAS를 다시 검사한다.

검사 결과로 수정안을 만들 경우 최초 출력·오류·수정 출력·지문을 각각 보존한다. 모델 재호출과 수정은 명시 실행 예산 안에서 별도 시도로 기록하며, 성공한 결과만 골라 최초 정확도로 보고하지 않는다. 자동으로 인용/끝점을 바꾸거나 검증을 완화해 저장시키지 않는다.

확인 기준: 올바른 초안 통과, 잘못된 인용/한정어/동명 구별/참조의 정확한 위치 보고, 검사 전후 자료 바이트와 상태 판본 동일, 검사 후 원문 변경 시 저장 거부. **실제 인용에 붙인 근거 없는 관계는 형식 검사를 통과할 수 있다는 대조 사례**도 계속 남겨 의미 보장을 과장하지 않는다.

### IMP-02 관계별 의미 계약

[현재 검증기](../../../core/modules/ontology/validation.py)는 술어·끝점 참조·한정어·중복을 확인한다. [어휘](../../../core/modules/ontology/constants.py)와 [제출 스키마](../../../core/runtime/extraction_schema.py)는 이미 버전별로 고정돼 있고 [의미 원문](../../../.agent/ontology_semantics.md)에 방향 지침도 있다. 추가할 대상은 이 기반과 연결되는 술어별 방향/끝점 역할/지원 유형/필수 보존 의미/금지 오용의 명세다. 같은 버전의 명세에서 설명·출력 제약·검사 기준을 일관되게 생성하는 방안을 우선 검토한다.

예를 들어 `precedes`는 사건 순서이며 `causes`의 근거가 아니고, 예정 출고의 주어가 특정 주문인지 일반 업무 과정인지 확인해야 한다. 넓은 개체 유형만으로 이 차이를 모두 잡을 수 없으므로 명확한 형식 오류와 원문 의미 검토를 구분한다. 충분히 검증되지 않은 유형 조합은 경고/검토로 시작하고, 유효한 원문 관계를 막는 계약은 강제하지 않는다. [RDFS의 domain/range](https://www.w3.org/TR/rdf-schema/#ch_domain)로 주체/객체의 클래스가 함의되는 의미를 입력 거부 조건과 혼동해 대상의 유형을 자동 보충하지 않는다.

Graphiti의 고정 소스 `enforce_edge_type_signatures`는 일부 유형 불일치에서 strict이면 간선을 버리고 아니면 `RELATES_TO`로 바꾼다. 흡수할 부분은 **명시적인 끝점 계약**이다. 우리 EP-01/08에 맞게 불일치를 원문 위치·원래 의미·검토 질문으로 남기며, 조용한 삭제나 일반 관계로의 약화는 채택하지 않는다. 후보에도 임의 새 술어를 허용하지 않는다.

확인 기준: 잘못된 방향/명백한 유형 오류를 검출하고 유효한 관계는 유지, 부정·조건·계획·관점이 다른 관계를 같은 것으로 합치지 않음, 표현할 수 없는 관계의 누락/보류가 드러남, 옛 버전 읽기·claim ID·기존 발행본 불변.

### IMP-03 보존 뒤 구조화와 누락 점검

Graphiti처럼 책임을 단계로 나누되 호출 수를 그대로 복제하지 않는다. 먼저 원문 절·표 행과 조건/예외/전언 문맥에서 명시 주장을 식별하고, 그 후 기존 관계·속성·한정어·출처로 표현하며, 마지막으로 원문 주장 목록과 정상 주장/미확인 후보/표현 한계의 대응을 확인하는 방안을 비교한다. 고정된 초기 개체 목록에 없다는 이유로 후반에 발견한 개체나 관계를 버리지 않는다. 전언의 직접 전달자와 원설명자, 사건 날짜와 시각도 점검 대상이다.

기존 스키마로 나눌 수 있는 수량·단위·조건·시점은 문장 속에만 묶지 않고 해당 필드를 사용한다. 동시에 분해 과정에서 조건의 공동 적용, 예외, 부정, 의무·금지의 뜻을 잃지 않아야 한다. 현재 표현할 수 없는 규범 논리는 D-062의 원문 텍스트 보존을 유지한다. 원문 문장과 구조화 결과를 중복된 별개 사실로 세거나, 모든 문장을 원자 사실로 분해했다고 가정하지 않는다.

주장 목록/대응표는 우선 실행 중간 산출물 후보이며 기존 그래프에 임의 collection을 추가하지 않는다. 생성자가 만든 체크리스트와 줄별 커버리지는 자체 점검 자료다. 전체 문장에 ID를 붙였다는 이유로 의미 보존100%를 선언하거나 독립 평가 질문으로 재사용하지 않는다.

확인 기준: 한 번의 추출과 같은 호출 안의 단계적 추출을 먼저 비교하고, 필요한 경우 추가 점검 호출을 분리해 효과를 측정한다. 내용 보존을 떨어뜨리지 않으면서 구조화 보존이 늘고, 미확인/후보/한계가 사라지지 않는지 확인한다. 모델 호출 수·실제 토큰·시간·저장 성공·새 의미 오류와 반복 차이도 함께 보고한다.

### IMP-04 범위를 지킨 대상 대응과 외부 용어

기존 EP-05·식별자 namespace·[문서 간 대응](../correspondences/PLAN.md)을 재사용한다. 검색으로 유사한 기존 개체를 찾더라도 원문/문서·발급 범위·유형·관점·시점·명시적 차이를 먼저 확인한다. 같은 코드·문구·벡터 점수는 동일성의 증명이 아니다. 실제 비교의 OR-27·서로 다른 B7·화면별 ‘처리 완료’가 반례다. 센터가 적히지 않은 선반의 센터는 주변의 같은 B7에서 전파하지 않는다. 이 source 지지는 범위 키의 일치 검사만으로 보장되지 않으므로 별도 의미 검토가 필요하다.

OLS 같은 외부 용어 조회는 표준 개념의 정의·동의어·계층·IRI를 찾는 보조 후보로 쓴다. 회사의 특정 주문/장치와 표준 클래스, 관련어와 동일어를 구분한다. 외부 응답은 외부 출처이며 원문이 주장한 사실이나 원문에 실제 있는 식별자가 아니다. 현재 entity.identifiers/evidence에 외부 IRI를 끼워 넣거나 가짜 원문 개체로 relation_candidates의 끝점을 만들지 않는다. 실제 도입에는 외부 용어 버전/정의·대응 종류·조회 출처·검토 상태를 담을 별도 계약이 필요하다. 검색 결과가 없으면 미해결로 남긴다.

확인 기준: 동명 이종 대상·코드 범위·종류/개체·다의어·obsolete 용어를 구분, 원문의 명시 별칭은 보존, 조회/후보 생성만으로 병합·전문가 승인·원문 근거 승격이 일어나지 않음. 후속 격리 검증에서 OLS HTTP 캡처/별도 sidecar 후보화를 실행했으며 native MCP/adapter 연결은 미검증이다. 원문의 명시적 비동일성을 판본에 연결해 전달하고 미해결 후보보다 우선하는지 추가 확인한다. namespace 차이만으로 모든 대상을 비동일하다고 일반화하지 않는다.

### IMP-05 시간과 충돌의 명시 표현

현재 상태: D-084에 따라 별도 시간 장부·조회 엔진 도입 및 후속 개발·재검증은 제외했다. 아래는 기존 시간 정보 보존 요구와 당시 조사·평가 기록이며 새 장부 구현을 예정한 작업 목록이 아니다.

현재 `qualifiers.time`·양태·provenance·전체파일 source_revision·저장 이력을 유지한다. 추가 조사 대상은 사건 발생일/시간, 누군가 말한 시점, 문서 작성 시점, 시스템에 기록한 시점, 주장의 적용 기간을 구분하는 시간 해석이다. 우선 원문 문자열과 역할을 보존하고, ISO 시각 등 비교용 파생값은 근거·기준 시각·시간대·정밀도·해석 규칙에 연결한다. 명시적 버전 계약 없이 기존 time 문자열을 객체로 바꾸거나 계산값으로 덮어쓰지 않는다. 날짜만 알려졌으면 자정을 실제 발생 시각으로 확정하지 않는다.

충돌은 같은 대상·조건·기간·주장 범위의 양립 불가 여부를 검토한 뒤 양쪽 claim과 근거에 연결한다. 새 문서/나중 시각만으로 옛 주장을 종료시키지 않는다. 명시적 변경/종료 근거와 실제 사건 시점을 확인하며 계획을 실행 완료로 바꾸지 않는다. 시간 순서가 다른 사실, 시점이 다른 유효 상태, 동시점 미해결 충돌을 구분하고 EP-09/RP-03의 사람 검토/이력 경계를 유지한다.

확인 기준: 현장 날짜 누락 탐지, 자정/시간대/상대 날짜의 불확실성 보존, 미래 계획과 과거 기록 구별, 동일 조건의 두 마감 값 동시 보존, 나중에 들어온 과거 기록과 명시적 정책 변경의 구별. 구조화 시간/충돌 검토 단위 추가에는 별도 스키마·권한·원장 호환 설계가 필요하다.

2026-10-29 사용자 예시로 평가 범위를 보완했다. ‘민수는 개발팀 / 개발팀은 VOC 미담당 / 2026년9월 인사팀 발령 / 조회 기준은2026년10월 / 인사팀은 VOC 담당’은 날짜 문자열의 보존을 넘어 **기준 시점에 유효한 관계를 선택하고 연결된 업무 규칙을 적용하는지**를 검증하는 사례다. 앞선 시간 관측 추가 실험에는 기준 시점 조회와 관계 경로 추론이 없어 이 효용을 평가하지 못했다. 현재 추가 관측 구현의 비채택을 시간에 따른 상태·규칙 해석 자체의 비채택으로 확대하지 않는다.

다음 비교의 원문에는 발령 이전 소속의 기준 시점, 발령의 실제 효력/예정 여부, 겸직 또는 이전 소속 종료 여부를 명시해 골드가 숨은 가정에 의존하지 않게 한다. 사용자의 원래 다섯 문장과 이러한 명시적 변형은 구분한다. 조회 기준 시각은 사례 입력으로 고정하며 시스템 실행일로 대체하지 않는다.

최종 비교는 동일 질문·원문으로 기준선과 시간 처리를 각각 실행해 현재/과거 답의 정확성, 근거 경로, 계획의 실제 사실 오확정, 과거 정보 덮기, 부당한 개인 업무 상속, 반복 차이와 추가 비용을 따로 측정한다. 원문에 접근한 LLM도 이 짧은 사례에 답할 수 있으므로 사례를 풀었다는 사실만으로 시간 구성요소의 개선을 주장하지 않는다. 이 절은 보완된 평가 기준이며 새 모델 비교나 시간 질의 엔진 구현 완료를 뜻하지 않는다.

같은 날 [두 번째 조회 실험](../../../evals/2026-10-30-temporal-query-v2/REPORT.md)에서 설명/실제 조건, 복합·역방향 계획, 개인 규칙·기간 예외·일부 정정과 근거 공유를 보완하고 새42문항으로 재검증했다. 개선 효과와 남은 구현 오류를 분리했으며, 메서드 동결 후 발견한 연도 생략 날짜 실패는 재실행해 지우지 않았다. 전체 완전 처리18/42(실행된 부분18/28)와 모델의 보완, 바이트 감소와 실제 토큰을 각각 보고한다. 약칭 전달·다른 이름/대상의 정정·종료/조건 미충족 판정은 여전히 구현 경계다. 이를 시간 장부 자체의 한계로 일반화하지 않는다.

### IMP-06 근거 의존성과 변경 미리보기

[현재 영향 조회](../knowledge/PLAN.md), D-076의 문서 선택 재검토/고정 입력/검증된 재개, RP-02를 재사용한다. 새 검토 대상은 결과 주장이 어떤 원문 구간/판본·다른 전제·해석 규칙에 의존하는지와, 변경 시 추가·수정·제거·미해결·재검토될 항목을 저장 전에 보여주는 비교다. 인용/조건/양태/출처가 바뀌면 ID가 같거나 값이 같아도 변경으로 취급한다. 형식적 도출 근거가 있더라도 전제 자체의 현실 진위를 증명하지 않는다.

증분 재추출은 변경 줄만 읽으면 된다는 가정으로 시작하지 않는다. 별칭·지시 대상·예외·표 머리글이 다른 구간 해석을 바꾸므로 의존 범위를 확실히 찾지 못하면 선택 문서 전체를 재검토한다. 현재 저장은 전체 그래프/CAS 계약이다. 부분 결과로 전체 그래프를 덮어쓰거나 새 원문 revision만 과거 주장에 붙이지 않는다. 이 실험적 방식의 재조립·stale 범위·승인 보류·실패 보존을 명세하기 전에는 운영 쓰기에 연결하지 않는다.

확인 기준: 추가/삭제/조건/별칭 변경과 서로 떨어진 구간의 의존 변화, 변경 중 원문/판단 상태 충돌, 실패 후 원문·그래프·이력 보존, 원래 주장과 과거 사람 판단의 감사 가능성. 명시된 변경 의존성과 단순 유사도 후보를 구분한다.

### IMP-07 검색 결과의 의미 보존 검사

키워드·벡터·그래프 경로의 결합 검색은 필요한 맥락을 찾는 후보 기술이다. 현재 추출은 EP-01의 전체 선택 범위를 유지하고, 검색으로 선택되지 않은 원문을 추출 대상에서 조용히 제외하지 않는다. 답변용 검색에서도 정답처럼 보이는 주장 하나만 반환하지 않고 해당 조건·예외·출처·판본·미해결 충돌의 반대편까지 필요한 근거로 확인한다. 현재 권한·current/stale/pending·complete/truncated/skipped 표시를 유지한다.

확인 기준: 질문별 답변/보류와 필요한 근거를 검색 전에 고정하고 키워드 기준선과 비교한다. 회수 수나 벡터 유사도만으로 성공을 판정하지 않는다. 도출 가능성 검사는 명시 전제의 보존 검사로 한정하고 자연어 원문 지지나 현실 진위의 인증으로 확대하지 않는다. 앞선 Graphiti 실행에서 검색/재순위화 호출은0이므로 그 실험으로 검색 개선을 주장하지 않는다.

### 적용 순서와 완료 조건

최신 선택은 위 후보별 새 표본 판단을 따른다. 다음 구현의 선행 조건은 조건부 권고한 **IMP-01 검사 서비스의 권한/동시성/플랫폼 경계와 유효한 전체 입력**이다. 명시 별칭/비동일 근거 보존·순서 차이 제거를 재사용하고, 관계 계약·명시 의존 설명·k6 문맥 검색은 한정된 보완 후보로 둔다. IMP-03 addon·IMP-05 새 시간 장부의 기본 추가와 IMP-06 미리보기 전체는 권고하지 않는다. IMP-07은 새 표본의 일부 개선으로 선택 기능의 추가 검증 가치가 생겼지만 기본 전환은 보류한다. 제품 연결이나 외부 MCP의 상시 의존성 추가는 수행하지 않았다.

실제 검증에서는 기존 비교 fixture를 개발 회귀로 쓰고, 최종 판정은 다른 분야의 새 미사용 원문·새 분리 세션·생성 전 고정 질문으로 수행한다. 한 번에 모든 후보를 합치지 않고 각 변경의 내용/구조화 보존·근거 없는 확정·후보 품질·저장 수용·반복 차이·비용 영향을 분리한다. 숫자로 정하지 않은 성능 목표를 달성했다고 표시하지 않으며, 새 거짓 확정이나 중요한 명시 내용 손실이 있으면 미해결로 보고한다. 최대 개발 교정 횟수와 원시 결과 보존은 [EVALUATION](EVALUATION.md)을 유지한다.

### 공식 출처와 확인 범위

- [Open Ontologies v2.1.0 도구 계약](https://github.com/fabio-rovai/open-ontologies/blob/v2.1.0/docs/tool-reference.md): scaffold/validate·SHACL·plan/diff·도출 근거·증분 추론의 기능 계약을 확인했다. 실제 scaffold/validate의 관측 결과는 앞선 비교 기록을 따른다. 나머지 기능은 이번에 실행하지 않았다.
- [Graphiti v0.31.2 설명](https://github.com/getzep/graphiti/blob/v0.31.2/README.md), [관계 처리 소스](https://github.com/getzep/graphiti/blob/v0.31.2/graphiti_core/utils/maintenance/edge_operations.py): 단계 분리·시간·사용자 정의 유형/끝점 계약·검색을 대조했다. 특히 유형 불일치의 drop/RELATES_TO 처리는 앞선 실험의 고정 로컬 소스에서도 확인했다. 이전 실험은 사용자 정의 스키마·증분 갱신·검색의 효과 시험이 아니다.
- [EBI OLS MCP](https://www.ebi.ac.uk/ols4/mcp): 용어/계층·IRI 조회 및 임베딩 검색 기능 설명을 확인했다. [공식 ontology API](https://www.ebi.ac.uk/ols4/api/ontologies)의 versionIri·정의/동의어 관련 메타데이터도 읽었다. 이 자료는 용어 후보화 설계 근거이며 원문 사실 근거가 아니다.
- [W3C SHACL](https://www.w3.org/TR/shacl/): 유형·자료형·카디널리티·속성 경로와 검증 결과 위치/메시지 계약을 참고했다. 모든 속성의 개수·필수값을 현실 업무 규칙으로 자동 강제하지 않는다. 이번에 RDF 저장 전환이나 SHACL 엔진을 설치하지 않았다.
- [Open Ontologies 증명 한계](https://github.com/fabio-rovai/open-ontologies/blob/main/docs/lean-certificates.md), [검색 투영의 도출 보존](https://github.com/fabio-rovai/open-ontologies/blob/main/docs/projection-entailment.md): 도출이 전제에서 성립한다는 검사와 전제의 진위를 구별했다. 두 페이지는 2026-10-29 조회의 변경 가능한 main 문서이며 v2.1.0의 모든 증명 기능을 인증하지 않는다.
