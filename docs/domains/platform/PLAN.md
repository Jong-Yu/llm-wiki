### 저장과 수집

- 알림 발생 이력, 수신함의 읽음/현재 상태·조회 인덱스, 페이지 확인 초안, 최종 승인, 공유 이어가기 요청과 실행 주체를 분리합니다. 인증된 tenant/user와 현재 허용 profile/행동으로 범위를 확인하고 클라이언트가 수신자·승인자 문자열을 임의 지정하지 못하게 합니다. 기존 인증정보와 정책은 자료 루트 밖에 유지합니다.
- 원본 4필드·고정 보고 ID/revision·원천 요청/영수증·서버 시각·행동 주체를 연결합니다. 본문은 원본/보고 참조로 읽으며 알림에 복제하지 않습니다. 알림 이력은 최신 승인 상태만 덮어쓰는 기록으로 축소하지 않습니다. 페이지 확인/승인 동시 변경은 CAS와 안정된 요청 ID로 조정합니다.
- 변환 보고는 PlanStore의 불변 보고 공개, 문서/관계 완료는 실제 saved/receipt, 실패·중단은 저장된 작업 사건에서 수집합니다. 질문/추가 질문 등 다른 업무도 동일 센터에 연결할 수 있도록 원천 계약을 분리하지만 첫 구현은 문서 처리의 승인 요청·완료·실패/중단을 대상으로 검증합니다.
- 원래 업무 저장과 알림 생성 사이의 각 실패/종료 지점을 정의하고 영속 전달 대기·중복 키·원천 영수증 기반 재조정으로 복구합니다. 알림 추가 실패 때문에 이미 성공한 문서/그래프를 실패로 바꾸거나 다시 저장하지 않습니다. 여러 파일을 잠금 아래 썼다는 이유만으로 원자성을 보장했다고 하지 않습니다.
- 서버에 아직 전달되지 않은 로컬 오류는 PC 보호 기록에 전송 대기로 남겨 재접속 때 멱등 전달합니다. PC가 꺼진 동안 서버가 그 사건을 관측했다고 표시하지 않습니다. lease 만료는 현재 조회에서 계산될 뿐 자동 저장 이벤트가 아니므로, 미완료 실행만 대상으로 하는 제한된 서버 확인 작업과 만료 사건 중복 키를 설계·검증합니다.

### 조회·부하·호환

- 커서 페이지 조회, 변경 순번 기반 증분 조회와 범위별 집계를 설계합니다. 현재 PersonalStore는 MAX_RECORDS=200/MAX_EVENTS=100 및 목록마다 전체 기록/이력을 읽는 구조이므로 알림함으로 그대로 사용하지 않습니다. CAS/멱등/영수증 패턴은 참고하고 저장 엔진·인덱스 구체안은 누적 이력 규모의 격리 측정으로 정합니다.
- 알림 건수·기기 수 증가에 따른 저장량/파일 수·읽기/쓰기 I/O·목록/증분 응답 시간을 측정합니다. 보관기간이나 자동 삭제를 임의 적용하지 않고 본문 중복·매 조회 전체 원문/이력 스캔을 피합니다. 오프라인 복귀는 커서 페이지로 미확인 사건을 나누어 가져오며 누락/중복·커서 무효화 동작을 정합니다.
- 서버의 안정된 작업/보고 식별자를 도입해 다른 PC에 로컬 journal이 없어도 상세를 읽도록 연결합니다. 기존 strict 작업 DTO와 보호 기록을 호환하고 과거 작업에 승인·실행 주체를 소급 부여하지 않습니다. 기존 미완료 보고를 승인 대상으로 연결하는 초기화는 원래 보고를 보존하고 실제 초기화 시각/출처를 구별하며 과거 알림 발생 시각을 만들어내지 않습니다.

### 승인과 기기 간 재개

- 서버에서 현재 권한·원본·보고와 페이지 확인 상태를 재검증하고 승인 영수증을 확정합니다. main/IPC에서도 같은 현재 기준을 검사합니다. 승인 경로가 필요한 새 문서 처리 계약을 버전/명시 모드로 식별해 구버전 클라이언트가 이를 우회 실행하지 못하게 하면서 기존 D-074 일반 부분 보존 API·이미 실행 중인 작업의 호환 범위를 명시합니다.
- 승인과 연결된 공유 이어가기 요청 ID를 모든 PC가 사용합니다. 같은 분석 request ID의 기존 멱등 접수는 재사용하되, 프로세스 시작 전에 서버가 실행 요청/기기/claim 식별자를 CAS로 확보하도록 추가합니다. 현재 claim은 같은 기준 revision이면 active run을 재전송할 수 있어 기존 lease만으로 두 PC 동시 최초 실행을 막지 못합니다. 실행 주체 식별자와 기존 claim/갱신/결과 제출의 연결 및 만료 후 이전 실행 차단을 검증합니다.
- 승인 PC와 실행 PC를 구분합니다. 현재 PC 준비 검사 통과 시 `승인하고 이 PC에서 계속`, 준비 불가 시 승인만 저장하고 실행 준비를 안내합니다. 다른 PC가 실행 중이면 상태 조회만 제공하며, 만료/중단은 실제 영수증·현재 산출물을 확인한 뒤 명시적 인계에서만 재개합니다. 이 PC의 local idle을 다른 PC 실행 중단으로 해석하지 않습니다.
- 승인 저장 미확인은 같은 승인 조회, 접수 미확인은 기존 분석 request 조회로 확인합니다. 영수증이 없을 때는 사용자의 명시 재시도만 보호 기록의 최초 본문/ID를 재전송하며 새 요청을 생성하지 않습니다. 승인 직후 앱 종료는 `승인됨·진행 전`으로 복원하고 조회만으로 새 실행을 시작하지 않습니다. 저장된 Wiki의 재저장을 막는 기존 재개 검사를 유지합니다.
- 현재 AnalysisService의 원본4MiB 차단과 CLI의 보존 등록 예외가 다릅니다. 사용자 PDF와 같은 약8.2MB 바이너리/170쪽/약314KB 변환 문자 규모에서 보존 등록 실행 준비를 검증하고 입력 경계별 크기 검사를 정합화합니다. 문서나 보고를 임의 축약해 우회하지 않습니다.

### 전달과 완료 조건

- 서버 알림을 먼저 보존하고 실행 중/숨김 상태의 앱에서 OS 알림을 보조 전송합니다. 알림 클릭은 인증 범위와 정확한 작업/보고를 확인한 뒤 화면만 엽니다. 완전 종료 동안에는 서버에 쌓고 다음 실행에서 가져옵니다. 종료된 PC로 즉시 푸시하는 상주 서비스는 이번 범위가 아닙니다.
- 완료 조건은 앱 종료 중 서버 사건 보존·두 PC 읽음/확인/승인 동기화·동시 승인/접수/실행 중복 방지·새 보고/권한 변경 거부·원천 저장 성공과 알림 실패의 분리/복구·서버와 PC 재시작·구기록 호환·보존입니다. 승인 전 실행0회, 승인 후 접수/실행 각1회, 추가OCR0회와 실제 크기 조건을 함께 확인합니다.
- 누적 알림 부하와 Windows 포터블 OS 알림 허용/거부/클릭·앱 숨김/종료를 실제 검증합니다. 호환 서버 API/저장부터 배포 후보를 만들고 새 앱을 연결하며 현재0.4.1 서버/앱 및 기존 사용자 기록을 변경 전에 대조합니다.

읽기 전용 조사와 미실행 범위는 [최초 기록](HISTORY.md#2026-11-24--ocr-알림승인-복원-계획-검토) 및 [서버 공유 계획 기록](HISTORY.md#2026-11-24--서버-알림-수집공유-승인과-기기별-실행-계획)을 따릅니다.

## 현재 상태

### 2026-11-24 — 알림·승인 0.5.0 공개

64px 알림 목록, 서버 공유 알림/읽음/페이지 판단/최종 승인, PDF 원본 대조와 기기별 이어가기를 소스 `35f011d`/`v0.5.0` 및 [0.5.0 Windows 포터블](https://github.com/Jong-Yu/llm-wiki-releases/releases/tag/app-0.5.0-portable)로 공개했습니다. 서버도 같은 코드로 재시작하고 기존 주소 메모를 갱신했습니다. 앱 빌드·릴리스70검사·Python1517검사(1513통과·Windows4skip), ZIP/런타임/포함 소스와 공개 다운로드를 검증했습니다. 기존 공개0.4.0·0.4.1 및 자산4개를 보존했습니다. 운영 계정의 실제 승인·이어가기와 Windows OS 알림은 별도 확인이 필요하며 [배포 기록](HISTORY.md#2026-11-24--알림승인-050-포터블-공개와-서버-반영)에 한계를 구분합니다.

### D-071~074 공통 서버 통합 (2026-10-28)

공통 연결 구현과 격리 통합 검증을 진행했습니다. 기존 자격 증명 초기화 호환 오류는 2026-10-29에 수정하고 해당 통합 검사를 재검증했습니다. 실제 검증과 운영 연결의 한계는 [HISTORY](HISTORY.md)에 기록했습니다.

- 같은 `create_application(policy, rulesets=...)`에 `/api/v1`와 인증된 `/mcp`를 유지합니다. 공개 가입·로그인 라우터와 middleware는 인증 담당 구현을 그대로 연결합니다. 기존 설정 오류를 자동 초기화로 덮지 않습니다.
- 공통 `Access` 응답에 선택적 `access_revision`을 추가하고 `core.api.dependencies.access_value(scope)`가 실제 scope의 새 값을 전달합니다. 예전 actor에 새 필드를 주입하지 않으며 신규 pagination 기준은 access_revision이 있으면 이를 사용합니다.
- MCP `wiki_read`는 전체 `content/revision`을 유지하고 저장 담당 파서의 `metadata/body/body_start_line/body_revision/document_id`를 추가합니다. `wiki_write`는 선택적 `origin`(`human/ai/unknown`, 생략 시 unknown)과 `reason`을 받고 서버가 인증한 actor만 `WikiStore.save`에 전달합니다.
- 기본 등록·고정 입력·MD/그래프 저장은 실제 `JobStore`/`InputStore`/`ResultStore`와 연결했습니다. `wiki_write`는 HTTP와 같은 `history.save_content(..., prepare_metadata=True)`를 사용하며 작성 원장 미확정도 저장 성공과 구분해 반환합니다.
- `core/tests/poc_mcp/`에 격리 API/MCP·stdio·실제 loopback HTTP 통합을 추가했습니다. 운영 자료/설정·실제 모델·UI 검증은 이 세션에서 수행하지 않았습니다.
- 공개 구현: `create_application(policy, *, rulesets=None, auth=None, credential_key_path=None)`는 정책 검증 후 `initialize_auth`를 호출하고 `app.state.auth`를 연결합니다. HTTP CLI `--credential-key-file`이 같은 인자를 전달합니다. cryptography 50.0.2·PyYAML 6.0.2를 requirements/lock에 고정했으며 현재 `.venv`의 설치도 확인했습니다.
- `analysis_registration_create(tenant, request_id, source_ref, document, title, conversion_ref=None)`는 `JobStore.create_registration`을 호출합니다. 본문/원본/작업 저장을 MCP에서 재구현하지 않습니다.
- **기존 토큰 시작 호환 해결**: 일반 `credentials/*.token`만 있을 때 최초 키 생성을 허용하고 기존 Bearer 인증·정책·토큰을 보존합니다. 암호문·미완료 가입·알 수 없는 항목·링크가 있으면 키 손실로 계속 거부합니다. 자동 token 이관/재발급은 하지 않습니다. 관련 legacy 통합 재검증과 실제 Mac loopback API/MCP 초기화를 확인했습니다.
- 신규 서버 전용 `python -m tools.initialize_server --server-root <새 절대 경로>`는 기존 경로를 거부하며 빈 정책·data와 `initialize_auth` 키만 준비합니다. 정상 시작에는 이 도구를 호출하지 않습니다. 기존 오류를 우회하는 자동 초기화는 없습니다.
- Linux 서비스 생성은 자료 루트와 보호 정책의 전용 부모 폴더에 쓰기를 허용해 가입의 정책/암호문/잠금 공개를 지원합니다. 실제 systemd/WSL 배포는 미실행입니다.
