## 후속 수정 — 지침 명칭과 목록 파일명

편집에서는 정보 배지를 제거하고 **템플릿 이름 → 양식 파일 → 지침**을 바로 표시한다. 목록의 개수 표시는 없애고 그 자리에 파일명을 옮겼으며 이름 아래 중복 파일명도 제거했다. 등록·상세·편집·채팅 선택과 요청 정보의 명칭은 사용자의 최종 정정에 따라 **지침**으로 통일한다. 상단 취소·저장, 등록의 기존 순서와 상세 정보 칩은 유지한다.

## 2026-11-15 이전 시안: 실제 문서 화면 기준으로 교정한 템플릿 관리

2026-11-15 사용자가 템플릿 메뉴의 배치가 여전히 기존 화면과 다르다고 지적했다. 직전 시안은 공통 컴포넌트 일부를 재사용했고 조작 검사를 통과했으나, 이를 화면 전체의 통일성 확인으로 표현한 것은 부정확했다. 실제 `DocumentLibrary`와 비교하니 검색·필터 도구줄과 페이지 이동이 빠져 있었고, 상시 “내 템플릿” 건수·설명과 시안 상단 설명 띠를 추가했다. 행의 `data-secondary` 누락, 500px 미만 열 숨김, 상세·폼의 별도 720px 중앙 정렬, 신규 등록의 상단 행동도 기존 기준과 달랐다.

실제 화면에서 가져온 범위는 다음과 같다.

- 목록은 `DocumentLibrary`의 section·상단 행동·검색/필터 도구줄·표·페이지 이동 구성을 따른다. Enter 검색, 초기화, 형식 필터와 페이지당 20개 이동을 연결했다. `data-secondary`·`data-selected` 행 표시를 적용하고 상시 소개 줄과 좁은 화면의 별도 열 숨김을 제거했다.
- 신규 등록은 `RegisterDocumentPage`의 page/grid/section과 `ImportDocumentForm`의 fieldset·파일 선택 영역·하단 행동 배치를 사용한다. 파일 선택·템플릿 이름·작성 룰만 입력하고 하단 **템플릿 등록**으로 저장한다. 이전의 상단 등록 행동·하단 취소·예시 파일 버튼은 제거했다. 이름과 파일이 없으면 기존 등록 화면처럼 등록 버튼을 비활성으로 표시한다.
- 편집은 `DocumentEditor`의 상단 취소/저장과 편집 도구줄을, 상세는 `ManageDocumentContent`의 root/documentBody를 기준으로 왼쪽에 맞춘다. 별도 720px 중앙 정렬을 제거했다.
- 시안 상단 설명 띠를 없애고 실제 `AppShell`의 외곽·본문 넘침 처리를 사용한다. 시연 높이는 900px이다. 시안 래퍼의 링크 색 우선순위를 낮춰 실제 위치 경로 색을 덮지 않도록 했다.

왼쪽 템플릿 메뉴에서 이름·양식 파일·룰을 관리하고, **AI 채팅에서 선택 → 요청 → 같은 대화의 파일 카드·내용 미리보기**로 이어지는 흐름은 유지한다. 채팅은 기존 실제 컴포넌트를 사용한다. 제품 소스·저장 계약을 변경하지 않았으며 실제 파일 해석·AI 실행·파일 생성·룰/서식 검사는 미연결이다.

## 2026-11-14 제안: 한 번 등록하고 작성할 때 선택

사용자가 설명한 프로젝트 지침 방식에 맞춰 흐름을 단순화했다. **저장된 템플릿 = 이름 + 양식 파일 + 작성 룰**이며, 산출물을 만들 때 이 묶음을 선택한다. 관리와 작성은 서로 다른 화면이고 같은 시안 안에서는 메모리의 템플릿 목록을 공유한다.

- **템플릿 등록·관리**: 등록된 목록에서 양식 파일과 룰을 확인한다. 신규 등록과 편집은 이름·파일·자연어 룰의 세 입력만 둔다. 저장 후 다시 입력하지 않고 선택해서 사용할 수 있다.
- **산출물 만들기**: 프로젝트 지식이 준비된 상태에서 템플릿을 선택하고 요청을 입력한다. 선택한 파일과 저장된 룰이 함께 적용됨을 표시하며 룰 상세는 펼쳐 볼 수 있다. 작성 도중 관리 화면을 다녀와도 요청 초안을 유지한다.

작성 영역 지정·보호 요소·출력 형식·사용 방식은 기본 등록 과정에서 제외했다. 원본 형식에 맞춰 작성하는 것을 목표로 하며, 서식 해석이나 정책에 모호함이 있을 때만 후속 질문으로 확인해야 한다. 내용 규칙 검사와 실제 파일 서식 검사는 여전히 구별해야 한다.

아래의 세 가지 배치와 형식별 상세 설정은 이전 탐색 기록이다. 현재 사용 흐름과 기본 노출 범위는 이 절을 우선한다.

| 채팅에서 선택 | 작성 중인 질문 옆에서 양식을 선택하고 등록·편집 후 같은 대화로 복귀      | 반복해서 사용하는 양식이 있고 대화가 작업의 중심일 때 | 템플릿 관리의 발견성이 상대적으로 낮음  |

세 안은 캐러셀에서 전환하며 현재 창 안의 각 작업 상태를 유지한다. 보관함은 원본 파일 형식에 맞는 양식 미리보기와 작성 규칙을 함께 보여 준다. 단계형은 이미 완료한 단계로 돌아갈 수 있고, 수정한 규칙이 이번 요청용인지 새 템플릿으로 저장할 것인지 구분한다. 호스트 디자인 도구가 있으면 안별 작업 영역 여백을 16~32px로 비교할 수 있다.

보관함의 추가 템플릿 두 개와 단계별 저장 동작은 모의 예시다. 세 안 모두 파일 변환·실제 저장·AI 실행은 연결하지 않았다. 기존 단일 채팅 시안은 그대로 보존하고, 비교용 진입점은 `variants.tsx`와 `variants-fragment.html`로 분리했다.

## 특정 파일 형식에 종속되지 않는 템플릿

“템플릿이 MD여야 하는 것처럼 보인다”는 후속 피드백에 따라 세 안의 등록·미리보기·결과 표시를 교정했다. 템플릿을 **원본 양식 + 채울 영역 + 보존할 요소 + 작성 규칙 + 결과 형식**으로 다룬다. Markdown은 직접 정의에 사용할 수 있는 선택지 하나다. 원본을 일괄 Markdown으로 바꾸는 흐름을 전제하지 않는다.

| 원본 계열      | 사용자에게 보여 줄 기준                   | 확인할 보존 요소                                 |
| -------------- | ----------------------------------------- | ------------------------------------------------ |
| Word·한글 문서 | 문단·표·작성 필드                         | 머리말·꼬리말·스타일·페이지 배치                 |
| PowerPoint     | 슬라이드·텍스트 상자·그림 자리            | 마스터·로고·배치·반복 슬라이드                   |
| Excel          | 시트·셀·표 범위                           | 수식·병합·서식·보호 셀                           |
| PDF·이미지     | 참고할 페이지·구역                        | 편집 필드 유무·읽기 정확도·원본 채우기 가능 여부 |
| 링크·기타 파일 | 접근 가능한 원본과 사용할 범위            | 접근 권한·해석 가능성·대체 작성 방식             |
| 직접 정의      | 자연어 또는 Markdown으로 작성한 항목·순서 | 사용자가 지정한 구조·작성 규칙                   |

등록 진입은 **파일 가져오기 / 링크로 가져오기 / 직접 정의**다. 파일 선택은 확장자로 막지 않고 확인이 필요한 원본도 등록할 수 있게 한다. 원본 보관, 미리보기, 작성 위치 인식, 서식 유지, 출력은 각각 다른 능력이므로 “지원” 한 단어로 묶지 않는다. 제품 구현에서는 원본을 보존하고 가능한 작업과 확인할 부분을 따로 보여 주어야 한다.

사용 방식은 **원본 유지·빈칸 채우기 / 구조 따라 새로 작성 / 참고해 재구성**으로 구분한다. 작성 위치나 서식 보존이 확인되지 않은 파일·링크와 PDF·이미지 예시는 원본 채우기를 비활성화한다. 입력과 결과 형식은 별도로 선택하며 PPTX→DOCX처럼 달라지면 구조 따라 작성으로 전환한다. 이때 배치가 같다고 보장하지 않는다.

현재 공통 `TemplateAsset` 컴포넌트의 미리보기와 작성 영역 선택은 개념 예시이며 원본 렌더러·실제 매핑 저장이 아니다. 실제 파일은 이름과 확장자만 읽고 본문을 읽거나 전송하지 않는다. 링크도 주소만 검사하며 접근하지 않는다. 미확인 원본은 등록 후 작성 대기로 남긴다. 결과는 **내용 검토용 초안**이며 파일 생성 미연결·파일 서식 검사 미실행을 별도로 표시한다.

최신 비교 진입점은 `formats-fragment.html`이며 보관함 → 채팅 → 단계형 순서다. [형식별 UI 검사](../../test-results/template-ui-formats-20261114/verification.json) 9묶음과 채팅형 6흐름·단계형 11항목을 확인했다. PPTX/DOCX/XLSX 미리보기, 출력 변경, PDF·이미지의 참고 모드, 자연어 직접 정의, 기타 파일·MD 파일의 미확인 등록, 링크 검증, 736·320px 재배치와 오류·중복 ID·fetch/XHR 없음이 포함된다. 초기 브라우저 검사는 문서 머리말·수식의 선택자 문구를 실제 예시에 맞춰 고친 뒤 통과했다. 위의 789,041바이트 비교 검증과 아래의 초기 채팅 검증은 교정 이전 기록이다.

## 채팅형 기준 세부 설계

별도 전역 메뉴를 늘리지 않고 **AI 채팅 입력창의 템플릿 선택**에서 시작한다. 사용 중인 문서·질문을 유지한 채 등록·관리를 열고, 저장 후 같은 요청으로 돌아온다. 새 템플릿 등록과 관리 편집은 채팅 작업 영역 안의 최대 720px 폼이다. 업무 모달은 사용하지 않는다.

| 화면           | 먼저 보여 줄 내용                                       | 주행동                     |
| -------------- | ------------------------------------------------------- | -------------------------- |
| 템플릿 선택    | 기본 답변, 내 템플릿, 기존 기본 양식                    | 이 요청에 선택             |
| 새 템플릿 등록 | 이름 → 원본 양식·작성 영역·결과 형식 → 작성 규칙        | 내 템플릿에 저장하고 선택  |
| 내 템플릿      | 이름·용도와 검색, 선택/편집의 구분                      | 사용할 템플릿 선택         |
| 요청 작성      | 참고 자료와 선택한 템플릿을 구별, 이번 요청의 추가 규칙 | 작성 요청                  |
| 확인 질문      | 충돌한 두 내용·출처, 미결정 사항과 선택지               | 답변 반영                  |
| 생성 결과      | 본문, 검사 요약, 작성 당시 설정                         | 필요한 항목 확인·수정      |
| 검사 상세      | 적용 규칙, 해당 구절, 근거, 상태와 다음 행동            | 해당 항목 수정 또는 재검사 |

처음에는 내 템플릿으로 등록하는 방향을 제안한다. 팀 공유·관리 권한과 조직 기본 템플릿은 이번 시안에 포함하지 않는다. 현재 네 가지 기본 양식(비교 보고서·매핑표·타임라인·브리핑)은 유지한다. 검색과 명시적인 대화 복귀로 채팅 안쪽에 있는 관리 기능의 발견성을 보완한다.

## 양식과 규칙을 구분하는 이유

- **양식**은 원본의 구조·배치·작성 위치다. 문서의 제목과 표뿐 아니라 슬라이드의 배치, 시트의 셀·수식도 포함한다. 작성할 영역과 보존할 요소를 구분해서 확인하며 양식 파일을 원문 근거 목록에 자동으로 포함하지 않는다.
- **작성 규칙**은 반드시 넣을 내용, 금지 표현, 근거 표시, 정책·수치 조건이다. 자연어로 입력하고 항목을 추가·제거한다. 사용자가 정규식이나 검사기를 설정하게 하지 않는다.
- 파일에 양식과 규칙이 섞이면 가져온 결과를 두 영역에 나눠 확인하게 한다. 규칙으로 보이는 문장이 있다는 이유만으로 원문 사실을 덮어쓰지 않는다. 자동 분리의 정확도와 복잡한 문서 서식 보존은 별도 검증 대상이다.
- **이번 요청 규칙**은 선택한 템플릿 위에 추가하는 일회성 조건이다. 저장된 템플릿을 바꾸는 편집 행동과 구별한다. 생성 결과에는 작성 당시 양식·규칙·확정 답변을 고정해 보여 준다.

## 질문에서 검사까지

원문은 “잠긴 문서는 누구도 수정할 수 없음”, 작성 규칙은 “검토자는 잠긴 문서를 수정할 수 있음”이다. 질문에는 두 문장을 함께 보여 주고 현재 정책 유지, 변경안으로 작성, 아직 미정의 의미를 구별한다. 변경안은 현재 서버 정책을 수정했다는 뜻이 아니다. 현재의 수정 거부와 변경 필요 사항을 함께 남긴다. ‘다르게 정하기’로 본인 문서에만 예외 허용 같은 조건도 입력한다. 시안에서는 자유 답변 해석을 연결하지 않았음을 밝히고 입력을 유지하며 대기한다. 제품에서는 이 조건을 다시 확인하는 질문까지 이어져야 한다.

필수 너비가 빠졌을 때는 별도 질문을 한다. 선택지에는 기본 답변을 미리 확정하지 않는다. 일부만 답하면 확정한 답변을 유지하고 남은 질문만 다시 표시한다. 필수 결정이 ‘미정’이면 작성 대기를 유지한다. 모든 불확실성을 무조건 질문으로 바꾸는 대신, 산출물의 의미·정책·필수 형식에 영향을 주는 것부터 묻는다.

원문 부재의 경우 사용자 허용에 따른 **가설 초안**은 별도 분기다. 필수 결정을 미룬 채 확정 설계서로 생성하는 것과 다르다. 가설임을 문서와 검사에 표시하고 원문 대조는 검사 불가로 남긴다. 이 분기는 이전 검증에서 확인했으며 이번 클릭 시안의 기본 경로에는 넣지 않는다.

검사 요약은 결과 제목 가까이 **내용 구조 확인 · 내용 규칙 확인 필요 · 원문 대조 검사 불가 · 파일 서식 검사 미실행**처럼 검사 영역과 상태를 함께 표현한다. 제목이나 내용 구조 확인을 파일의 배치·서식 보존 검사로 표시하지 않는다. 긴 본문을 모두 읽기 전에 경고를 알아볼 수 있다. 상세에는 위반한 구절, 규칙, 원문 또는 최신 답변, 해결 행동이 있다. 검사 불가를 통과 건수에 섞지 않는다. 자동 검사 통과는 사람의 승인과 구별한다.

설정이나 답변을 바꾸면 이전 생성물을 보존하고 ‘변경 전 기준으로 검사됨’을 표시한다. **검사만 다시 실행**과 **본문 수정·재생성**은 다른 행동이다. 새 규칙에 대한 검사를 실행했다는 이유로 기존 본문이 수정된 것으로 표시하지 않는다.

## 정상 흐름 밖의 상태

| 상황                            | 표시와 복구 방향                                                  |
| ------------------------------- | ----------------------------------------------------------------- |
| 양식 없음                       | 빈 목록에서 새 템플릿 등록을 제공, 기본 답변은 계속 사용 가능     |

| 일부 서식 변환·규칙 분리 불확실 | 변환하지 못한 부분을 저장 전에 표시, 확인 후 저장                 |

| 원문 없음                       | 자료 보완 또는 명시적으로 허용한 가설 초안, 대조 검사는 검사 불가 |

| 저장 결과 미확인                | 기존 요청의 저장 결과 확인, 자동 중복 저장 금지                   |
| 템플릿 편집 충돌                | 내 초안과 최신본 비교, 기존 결과의 당시 설정 보존                 |

뒤의 저장·변환·서버 오류는 제품 구현 시 필요한 설계 조건이다. 로컬 메모리 시안으로 실제 저장·경쟁·실패 복구가 검증되었다고 주장하지 않는다.

## 현재 화면과 재사용 경계

현재 채팅을 `app/tests/chat-states`의 격리 bridge로 실행하고 1280×900에서 확인했다. 현재 AppShell, 전역 메뉴, 테마 토큰, 공통 입력·버튼과 채팅 본문/입력창의 컴포넌트·스타일을 재사용한다. 대화 목록과 ＋ 메뉴도 실제 ChatHistoryPanel·ComposerMenu를 사용한다. 제품 파일과 기존 기본 양식 상수는 수정하지 않는다. 기존 첫 화면과 시안을 같은 1280×900 크기로 확인했으며, 시안에는 Nori 예시 자료와 요청 초안이 추가되어 있다. 기존 빈 질문의 추천 문장은 이 작성 중 상태에서 표시하지 않았다.

시안 전용 영역은 템플릿 선택·등록·관리, 일회성 규칙, 확인 질문, 검사 상세 및 이들의 메모리 상태 전이다. 현재 ChatComposer의 선택 목록은 기본 양식 상수에 묶여 있어 시안의 새 선택 UI는 별도 구성하되 기존 입력창 스타일을 사용한다. 예시 Nori 자료·질문·검사 결과는 모의 데이터다. AI를 호출하거나 위키를 읽고 쓰지 않는다.

인라인 표시에 맞춰 AppShell의 화면 고정 배치를 상대 배치와 최소 높이로 바꿨다. 전역 메뉴 항목과 위치는 유지한다. 시안 밖 메뉴도 경로 이동은 하지만 해당 제품 화면 대신 범위 안내와 대화 복귀를 보여 준다. 제품 전체 탐색의 대체 구현이 아니다.

현재 템플릿 선택은 확장자 제한 없이 파일명·형식만 반영한다. `.md`·`.txt`를 포함해 실제 템플릿 본문 해석은 연결하지 않았다. 채팅의 참고 자료 첨부용 텍스트 읽기와 템플릿 등록은 별개다. DOCX/HWPX/PPTX/XLSX/PDF·이미지의 실제 해석·서식 보존·내보내기는 미구현·미검증이며 등록만으로 이를 보장하지 않는다.

## 초기 채팅 시안 확인 결과

- [브라우저 검증](../../test-results/template-ui-proposal-20261114/verification.json): 8개 과업 묶음 통과. 등록 입력 오류, 초안·질문 왕복 보존, 지원하지 않는 파일의 원래 입력 보존, Markdown 읽기, 저장 후 선택, 요청 규칙 분리, 비답변·부분 답변·미정 대기, 변경안과 현행 423 병기, 수정과 재검사 구별, 검사 불가 유지, 답변 변경 시 확정값·이전 결과 보존을 확인했다.
- 1280px 흐름과 1024·736·390·320px 결과 화면, 320px 등록 폼의 가로 넘침 없음, 라이트/다크 화면을 확인했다. 브라우저 런타임 오류는 없었다. [선택](../../test-results/template-ui-proposal-20261114/proposal-picker.png) · [등록](../../test-results/template-ui-proposal-20261114/proposal-register.png) · [결과](../../test-results/template-ui-proposal-20261114/proposal-result.png).
- 시안 범위 strict TypeScript, typed oxlint, 소스/스타일 포맷 검사와 Vite 번들이 통과했다. 대화에 표시하는 자급형 시안은 1 MB 미만이다. 전체 제품 빌드와 실제 서버·AI 연결 시험은 수행하지 않았다.
- [인라인 환경 확인](../../test-results/template-ui-proposal-20261114/inline-verification.json): sandboxed iframe에서 등록 → 저장 → 작성 → 답변 반영 → 결과 수정·재검사를 통과했다. 이 환경에서는 네이티브 폼 제출이 막혀 시안 버튼을 로컬 이벤트로 연결했다. 최종 번들은 746,082바이트이고 해당 경로의 런타임·콘솔 오류는 없었다.
- 독립 UX 검토에서 기존 확정 답변 초기화, 긴 결과 뒤의 경고, 정책 선택지의 한계를 확인했다. 기존 값 불러오기, 본문 위 검사 요약, 자유 답변 입력과 시안 대기 안내로 보완했다.
- 호스트에는 예시 화면·선택·확정값만 전달한다. 직접 작성한 규칙·파일 본문·질문은 보내지 않으며 현재 시안 메모리에서만 유지한다. 사용자 양식을 원래 예시로 바꾼 결과처럼 복원하지 않는다.

실제 저장/충돌, 양식·규칙 자동 분리, 임의 템플릿에 따른 생성·검사, 자유 답변의 의미 해석, 복잡한 문서 서식 보존은 남은 구현·검증 범위다. 산출물 검토 뒤 다음 범위를 결정한다.

## 재현

`app` 경로에서 Node 24와 설치된 프로젝트 의존성을 사용한다.

```sh
node node_modules/typescript/bin/tsc -p tests/template-ui-proposal/tsconfig.json --noEmit
node tests/template-ui-proposal/build.mjs <절대경로>/template-workflow.html
node tests/template-ui-proposal/verify.mjs <격리 Vite 미리보기 URL>
node tests/template-ui-proposal/build.mjs <절대경로>/template-design-options.html variants.tsx variants-fragment.html
node tests/template-ui-proposal/verify-options.mjs
node tests/template-ui-proposal/build.mjs <절대경로>/template-format-options.html variants.tsx formats-fragment.html
node tests/template-ui-proposal/verify-formats.mjs
```

`index.html`은 격리 Vite 미리보기 진입점, `fragment.html`은 대화 안 표시를 위한 골격이다. `renderer.tsx`의 bridge는 예시 공개 상태만 메모리로 반환한다. 새 제품 라우트나 저장 API는 추가하지 않는다.
